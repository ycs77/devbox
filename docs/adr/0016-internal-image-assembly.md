# Keep image assembly behind Devbox operations

ADR-0029 supersedes per-Toolchain Workspace candidates and assembly, ADR-0030 removes the public `sync` command, ADR-0032 removes persisted Workspace identity, ADR-0034 introduces the explicit public build pipeline and removes post-build verification, and ADR-0035 folds Base materialization into that single Workspace build. Build accepts one fully resolved Platform plan, generates the machine-owned Dockerfile, and invokes Docker directly against `devbox-workspace:latest`.

Devbox exposes the public global `build` command but no internal-artifact targets. `update` resolves and atomically publishes the exact Platform lock without invoking Docker; `build` alone consumes that lock, regenerates the common Workspace context, and publishes `devbox-workspace:latest`; `up` never invokes Build. AI Agent and Devbox-added Node-tool installation occurs later in the Sandbox entrypoint and never calls the Build module.

The Build module accepts one immutable, fully resolved current Platform plan. It owns Workspace-context generation, Docker invocation, cancellation, and publication of `devbox-workspace:latest`, while never reading Project or Local configuration, resolving upstream versions, activating or serializing an existing Platform lock, rendering Compose, or managing Sandbox lifecycle.

## Superseded historical candidate and fingerprint design

One plan carries exactly one active or in-memory candidate Platform snapshot plus zero or more selected Toolchains, so every requested Workspace is derived from the same generation of exact entries. When a Base candidate does not yet have its content-addressed local image ID, Build materializes it first and returns the completed prepared snapshot with that ID; the caller alone decides whether and when to activate it.

Each requested Workspace carries one caller-supplied opaque correlation key that never participates in artifact identity. A successful result maps every unique request key to its computed fingerprint and verified stable reference, allowing Build to deduplicate identical semantic inputs without making callers reproduce its canonicalization; duplicate keys are invalid. The optional Base result separately returns its verified stable tag and content-addressed image ID.

Its sole external operation is `prepare({ plan, signal })`, where the operation-scoped `AbortSignal` applies the shared cancellation contract. One plan may contain an optional candidate Base plus zero or more Workspace candidates, allowing Project Sync and global updates to use the same interface while Build hides dependency ordering, deduplication, serial candidate scheduling, and publication sequencing. Callers do not orchestrate separate Base and Workspace build methods.

The first release invokes at most one `docker build` process at a time: an optional Base candidate first, followed by Workspace candidates in deterministic fingerprint order. The selected Docker builder may parallelize work within that one build, but Devbox adds no cross-candidate concurrency until measurements establish a need.

`prepare({ plan, signal })` succeeds only when every requested artifact is ready and returns no partial-success result. After the first failure or cancellation, Build schedules no new candidate work, while already running work follows the shared child-process cancellation contract and any artifact that completed verification may retain its stable tag. A later call rechecks and reuses those safe results; Build never rolls them back merely to simulate transactionality.

The production adapter at Build's internal Docker-process seam invokes `docker build` directly with an argument array and no shell, streams Docker's native output, and preserves its exit status. Tests replace that adapter rather than introducing a Docker Engine API client; Sandbox lifecycle continues to use the already selected `docker compose` CLI path, so Devbox has one process-based Docker integration model.

Build owns one packaged Recipe catalog with exactly four independently versioned artifact recipes: Base, Node Runtime, PHP Runtime, and Workspace assembly. Each uses a recipe-local monotonically increasing integer rather than the CLI package version or a content hash. An artifact recipe is the deep module that owns its checked-in Dockerfile templates, disposable-context layout, controlled build arguments, assembly steps, and verification contract; the Node recipe also owns package-manager installation, while the PHP recipe owns extension build and enablement. Those implementation parts do not expose separate recipe versions. Any change that can alter the produced artifact or its verified contract increments the owning recipe version, while comments, refactors, and byte-identical packaging changes do not. Callers still supply only typed domain plans and never Dockerfiles, template fragments, or context content.

Recipe activation follows artifact identity rather than one package-wide generation. A packaged Base recipe is used only by explicit Base update and is represented after materialization by the candidate Base image ID, never by a recipe field in the active Platform lock or Workspace fingerprint. The current Node or PHP Runtime recipe version participates only in fingerprints selecting that Runtime, while the current Workspace recipe version participates in every Workspace fingerprint. Installing a CLI writes no Devbox or Docker state; the next Project Sync or global Platform update computes desired Workspace fingerprints from the packaged catalog, builds any new identities, and publishes retained Compose last. Built-in initialization suggestions and Compose rendering are not artifact recipes and do not change image identity.

Image readiness and reuse require no host-side registry or verification metadata file. Build verifies a materialized Base candidate before assigning its `devbox-base:<image-id-hex>` tag, and the Platform lock records the exact local image ID that tag must resolve to. Build separately verifies each Workspace candidate before assigning its deterministic `devbox-workspace:<fingerprint>` tag, and later operations treat only matching stable tags as reusable. Docker stores both image kinds, while each retained generated Compose definition stores only the Project's synchronized Workspace image reference.

`sync`, `up`, `stop`, `down`, and `rm` never opportunistically remove a superseded Base or Workspace tag. The image-removal pass of `devbox cleanup` alone considers Devbox-owned `devbox-base:<image-id-hex>` and `devbox-workspace:<fingerprint>` tags while holding the exclusive user-scope lifecycle lock and evaluating current references rather than a stale-image list.

A Workspace tag remains protected while any retained generated Compose definition references it or any existing Sandbox container uses its image; the active Platform lock does not independently protect a Workspace image because its content-fingerprint identity can be rebuilt. Replacing a retained Compose reference protects the new desired tag, while an old actual image remains protected by its running or stopped container. Once container replacement, `down`, `rm`, or Cleanup itself removes that last container and no other Project's retained Compose references the tag, the Workspace tag becomes eligible for a later Cleanup plan without a Workspace registry, dirty state, or generation record.

The Base tag resolving to the active Platform lock's exact local image ID is always protected because ordinary Sync cannot reproduce its native-package transaction. Candidate or superseded Base tags become eligible once no active Platform lock entry identifies them; existing Workspace images remain self-contained and continue protecting any shared physical layers they need. Cleanup removes only Devbox tags, while Docker retains physical image content protected by another tag or non-Devbox reference.

Artifact reuse and Cleanup are version-aware, fail-closed operations. A CLI may reuse, retag, protect, or delete only a Docker tag, image, container, or network whose Devbox ownership and fingerprint or resource-identity contract it understands. Build reports state carrying an unknown newer contract as incompatible and leaves it unchanged rather than inferring from a familiar tag prefix or partial labels. Because unknown retained or Docker state may protect artifacts the older CLI cannot discover, global Cleanup aborts before any deletion when it observes such state. Installing an older CLI therefore cannot downgrade, reuse, or garbage-collect Docker artifacts created under a future identity schema.
