# Implement the CLI in TypeScript with one Go host helper

The initial Devbox CLI is an ESM TypeScript package published as `@ycs77/devbox` and installed globally with `npm install -g @ycs77/devbox`, accepting the prerequisite that the WSL2 host already provides Node.js and npm. Its `engines.node` range is `>=22`, intentionally allowing Node 22, Node 24, non-LTS releases, and future majors without a separate up-front compatibility matrix; concrete incompatibilities will be handled when observed rather than narrowing installation preemptively.

TypeScript production code is bundled with tsdown, tests run with Vitest, Oxlint is the sole linter, and Oxfmt is the sole formatter. One internal `devbox-host` binary written in Go provides only host primitives whose required semantics Node cannot supply without native addons; its first-release interface is limited to kernel advisory locks, while Project, Sync, Build, Docker, and presentation logic remain in TypeScript.

The CLI parser is `citty`. Its command definitions are thin adapters over Devbox operations; the Devbox presenter, not Citty, owns `Result` mapping, normal stdout and stderr, cancellation semantics, and public exit statuses. `@clack/prompts` is reserved for a genuinely required interactive TTY prompt or confirmation; it is not the general terminal-output layer, and a non-interactive command never prompts. CAC is excluded until its prototype-pollution path is fixed and re-evaluated; oclif and Clipanion add more framework structure than this MVP needs.

The main package depends on a compatible caret range of `@ycs77/devbox-linux-x64` releases containing the precompiled helper, so users need neither Go nor native npm compilation. The Devbox CLI and helper use independent SemVer lifecycles: rapid CLI releases do not republish or renumber an unchanged helper, while the platform package version is the `devbox-host` release version. The initial helper compatibility line is `1.x`; a main package declares the minimum helper it needs, such as `^1.1.0`, and every later `1.x` helper must remain backward-compatible with earlier `1.x` clients. A breaking helper contract requires a new helper major and a main-package dependency range that selects it.

The platform package includes `bin/devbox-host` as an internal packaged asset but declares no npm `bin` entry, so it does not expose a `devbox-host` shell command. Its package `exports` explicitly expose the helper asset and package metadata; the ESM main package locates both through Node's `import.meta.resolve()` and never searches `PATH` or infers a `node_modules` layout. The helper exposes a small independently versioned machine protocol and remains the narrow native seam for kernel advisory locks, while Project, Sync, Build, Docker, and presentation policy remain in TypeScript.

Before starting the helper, the main package requires the resolved platform-package version to satisfy its declared helper range rather than equal the CLI version. It then starts the resolved absolute helper path directly without a shell or `PATH` lookup and treats the first real `acquire` exchange as protocol validation: every request and response carries the exact supported protocol version, and a missing or non-executable helper, unsupported package version, malformed or wrong-version response, or premature helper exit fails before protected work with an instruction to reinstall the current exact CLI version. Devbox adds no separate hello exchange, pre-spawn access check, or per-launch binary hash; npm artifact integrity, package-range validation, the actual spawn result, and the versioned acquire exchange provide the relevant checks without a second handshake.

The repository is one pnpm workspace monorepo with root `pnpm-workspace.yaml` and `pnpm-lock.yaml`; the root `packageManager` field pins the development pnpm release. `packages/devbox` contains the TypeScript CLI, `packages/devbox-linux-x64` contains the independently publishable platform package, and `native/devbox-host` is the Go module whose release build is copied into that platform package. The Go source and platform package are one helper product rather than two independently versioned products.

CLI and helper releases publish independently and directly to each package's npm `latest` distribution tag rather than using a staging tag. Most CLI releases publish only `@ycs77/devbox` and keep their existing helper range. A compatible helper release first packs and verifies its immutable platform tarball and protocol behavior, then publishes `@ycs77/devbox-linux-x64`; because existing caret ranges may select that release during a later installation, every `1.x` helper publication is itself a compatibility activation point. A CLI that needs a higher compatible helper floor is published afterward with the raised caret range. A breaking helper major is not selected by earlier ranges.

npm provides no atomic multi-package publication. If a compatible helper publication succeeds and a dependent CLI publication fails, the helper remains published and must still work with every earlier CLI range that selects it; ordinary CLI installation continues to select the prior main-package release. Automation may retry an incomplete publication only with already verified immutable artifacts. Because npm never permits reusing a published name and version, a defective CLI or helper artifact is not replaced or silently rebuilt under that version; recovery publishes a newer patch release.

npm alone owns installing, updating, downgrading, and reinstalling the Devbox CLI package tree. The supported installation and update instruction is `npm install -g @ycs77/devbox`, which selects the main package's current `latest`; Devbox does not recommend a separate `npm update -g` workflow. Reinstallation may add an exact main-package version to the same command. npm package-tree replacement updates packaged CLI code, Built-in defaults, recipes, templates, and the selected helper dependency but performs no Devbox file migration, Platform operation, Docker work, or Project operation. The packages use no install lifecycle script for those effects.

The CLI package version is also independent of four persisted schema domains: Project configuration, Local configuration, the Platform lock, and retained generated Compose. Each format changes and declares its supported reader or migration range independently; installing a CLI does not bump any file merely to match the package. Project configuration uses supported readers without rewriting, Local configuration owns its forward migration and interactive recovery, the Platform lock separates structural migration from artifact-backed candidate activation, and generated Compose is replaced from current sources rather than field-migrated while supported older definitions retain their operational envelope. An operation loads only the formats its contract requires. Devbox has no package-wide state generation, cross-format migration transaction, or generic `migrate` operation.

Schema evolution is forward-only and commits valid state in dependency order rather than simulating one release-upgrade transaction. A lossless Local-configuration migration and any Project-fixed synchronization form one atomic commit before artifact work; a structural Platform-lock migration forms its own atomic commit, while an artifact-backed Platform change commits only through verified candidate activation; current generated Compose replaces the retained definition last. A later failure never reverses an earlier valid commit. A missing migration step, invalid intermediate document, or interruption before an atomic rename preserves that file's prior bytes; interruption after rename means the new schema is committed and the next operation resumes from the state actually present. Devbox writes no reverse migration, backup state, or rollback metadata, and cleanup-eligible temporary files or unreferenced artifacts carry no rollback meaning.

Installing an older CLI package does not create a supported downgrade of Devbox-managed state. A CLI that observes a future Project, Local, Platform-lock, generated-Compose, or machine-protocol version fails closed, reports the observed version and its supported range, and directs the user to reinstall a compatible newer CLI; it never guesses fields, applies a reverse migration, or invokes an unknown helper protocol. Users may deliberately edit the two supported human-owned YAML interfaces and accept any semantic or data loss, but machine-owned Platform and Compose state have no manual downgrade path. npm package replacement leaves every running Sandbox unchanged, and an incompatible older CLI does not claim that unchanged runtime is manageable.

Release recovery treats the installed package tree, resolved helper range and protocol, each persisted schema, the active Platform lock, verified image tags, retained desired Compose, and the actual Sandbox as an observed state vector rather than one upgrade status. npm, filesystem publication, Docker artifacts, and container lifecycle do not form a transaction. Recovery advances only from the commits that actually exist: reinstall the running exact CLI for a broken package or helper tree, reinstall a compatible newer CLI for future state, rerun the failed ordinary operation after a Local or Platform commit, reuse or later clean verified unreferenced tags, retry Sync while older Compose remains retained, and leave every running Sandbox unchanged until its separately defined lifecycle replaces it. Devbox adds no `upgrade` or `doctor` command and never claims cross-system rollback.

Devbox's public compatibility boundary follows human-facing use. It includes the `@ycs77/devbox` package name and supported npm installation flow, CLI commands, arguments, and exit-status semantics, the documented Project- and Local-configuration interfaces, and the observable conditions under which incompatible schema or protocol state is refused together with a supported recovery action; exact human-readable error prose remains unstable. The platform package and helper asset resolution, protocol frames, machine-owned Platform-lock and generated-Compose serialization, internal Compose envelope, recipe assets and versions, fingerprint encoding, Docker names and labels, candidate state, and module interfaces remain internal. Internal surfaces still use the version gates, migrations, and helper-major rules required for safe evolution, but they are not user-reliant CLI SemVer interfaces.

Devbox provides no self-update command, does not invoke npm, and does not query the registry to announce available CLI releases in the initial version. `devbox update` and `devbox update --base` remain Platform artifact operations and never update the CLI. A package-tree failure reports an npm command that reinstalls the running CLI's exact version, while schema and retained-state compatibility are evaluated only when the installed CLI later executes an ordinary Devbox operation.
