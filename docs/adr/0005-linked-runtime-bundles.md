# Assemble Workspace images from isolated Runtime bundles

The initial Runtime catalog supports PHP and Node only, and a Toolchain may select PHP, Node, both, or neither. Devbox packages each selected Base-profile-compatible Runtime under an isolated path and assembles the selected bundles into one immutable Workspace image. The resulting first-release layer chains are Base only, Base then Node, Base then PHP, and Base then Node then PHP. Every PHP Runtime bundle also contains a directly usable Composer installation, while Toolchains without PHP do not contain Composer. This lets PHP and Node invoke each other directly in one Sandbox; the first release does not depend on experimental image mounts, install Runtimes during container startup, or couple Workspace image assembly to the selected AI Agent. BuildKit `COPY --link` may assemble these bundles, but cross-combination physical layer reuse is a best-effort storage optimization rather than a first-release correctness, readiness, or compatibility requirement. When both Runtimes are selected, the versioned assembly recipe copies Node before PHP in one fixed order, reusing the larger observed Node layer without making ordering depend on mutable size measurements.

Composer's exact revision and official source-image digest are part of the complete PHP entry in the Platform lock. Resolution selects the newest stable Composer 2 revision whose declared PHP requirement accepts that entry's exact PHP revision, independently for each PHP release line. Build copies Composer from the resulting immutable official image into the isolated PHP Runtime bundle and verifies it with that PHP executable, so Composer changes rebuild and re-identify every affected PHP Runtime bundle and Workspace image through the normal Platform update boundary.

Each PHP Runtime bundle retains the official image's `phpize`, `php-config`, and PHP development headers alongside the executable and libraries. They may compile or inspect Project-local native code with the Base build toolchain, but the host-matched non-root Sandbox user cannot install into or mutate the image-owned PHP extension directories; this does not create a supported per-Project extension mechanism.

Runtime preparation may use the official source image's `docker-php-ext-configure`, `docker-php-ext-install`, `docker-php-ext-enable`, and `docker-php-source` helpers inside disposable Build stages. The final PHP Runtime bundle removes those helpers and `docker-php-entrypoint` because they assume source-image layout and writable system installation paths that the Sandbox does not provide. It retains PHP, PEAR and PECL, `phpize`, `php-config`, development headers, configuration, and the already built and verified extension set.

Every Node Runtime bundle contains directly usable npm, Corepack-backed pnpm, and npm-installed Yarn 1.x tools, while Toolchains without Node do not contain those package managers.

The exact npm, Corepack, default pnpm, and Yarn revisions and immutable npm-registry integrities are part of the complete Node entry in the Platform lock. The locked official Node source image supplies only the bootstrap npm used to install those candidate tools. Package-manager changes rebuild and re-identify every affected Node Runtime bundle and Workspace image through the normal Platform update boundary.

Build requires bootstrap npm from the locked official Node source image. It installs exact npm and Corepack revisions with npm, disables all inherited Corepack shims, sets `COREPACK_HOME` to an explicit directory inside the isolated Node Runtime bundle, installs the exact default pnpm there as Corepack's global Known Good Release, enables Corepack shims for pnpm only, and force-installs the exact Yarn 1.x revision with npm so no inherited Yarn shim can block or replace it. Resolution selects the newest npm and Corepack releases whose declared Node engines accept the exact locked Node revision, the newest pnpm release, and the newest Yarn 1.x release before Build runs; Build never installs mutable version ranges, and an incompatible resolved pnpm or Yarn release fails preparation rather than falling back.

At runtime, npm and Yarn always use the global revisions from the Runtime bundle, while pnpm's Corepack shim honors an exact `packageManager` pnpm revision in a Project's `package.json`. Without that field, pnpm uses the Platform-locked global Known Good Release. Corepack's strict project-manager check remains enabled, so invoking pnpm fails when `packageManager` declares npm or Yarn rather than creating a competing lockfile. Devbox does not wrap npm or Yarn to enforce the reverse check; those direct executables remain usable when a Project declares pnpm. Devbox sets `COREPACK_DEFAULT_TO_LATEST=0` so downloading a Project-selected pnpm revision cannot update that default or trigger an unpinned latest-version lookup, and sets `COREPACK_ENABLE_DOWNLOAD_PROMPT=0` so the required exact revision downloads consistently for interactive users and AI Agents without blocking on a prompt. The bundled Corepack home is writable by the Sandbox user through that container's writable layer; it has no Docker volume or host cache, so Project-selected revisions survive container stop and restart but are discarded on container replacement while the image-preloaded default remains. A Project-selected pnpm revision is Project-owned tooling input rather than a Platform-lock or Workspace-fingerprint input. Project package locks govern dependency graphs and do not determine the npm, pnpm, or Yarn executable revisions.

Each successfully assembled and verified Workspace image receives the stable local Docker tag `devbox-workspace:<fingerprint>`. The fingerprint's semantic inputs are the complete exact Base entry from the applicable Platform lock, the complete exact entry for each Runtime selected by the Toolchain and no unselected Runtime entry, and a versioned Devbox Workspace assembly recipe. The Project identity or path, ports, selected AI Agent, Local configuration fields that do not affect image assembly, generated Compose content, Sandbox container state and writable layer, Agent executable, and other mutable Sandbox state are excluded. Any change to an included Base, selected Runtime, or assembly-recipe input therefore produces another tag without changing running Sandboxes, while Projects with identical included inputs resolve to the same tag and image.

Fingerprint schema version 1 uses one constrained canonical JSON encoding rather than hashing ordinary YAML or serializer-dependent JSON and does not require the full RFC 8785 algorithm. Its fixed payload schema contains the fingerprint schema version, the Workspace assembly recipe version, the complete Base entry, and the selected Runtime entries. The encoder emits schema-defined object fields in fixed order, orders Runtime entries by family and then release line, emits no insignificant whitespace, uses one defined standard JSON string escaping, and permits only integers, strings, and objects; an empty Runtime selection is an empty object rather than an omitted or null field. Devbox hashes the resulting UTF-8 bytes with SHA-256 without truncation and formats the stable tag as `devbox-workspace:v1-<64 lowercase hexadecimal characters>`. Changing either the fingerprint schema version or the assembly recipe version invalidates prior identities through the fingerprint itself and requires no persistent generation metadata.

## Runtime assembly evidence

On 2026-08-02, a disposable prototype on WSL2 `linux/amd64` with Docker Engine 29.3.1 and BuildKit 0.28.1 relocated digest-pinned PHP 8.4.24 and Node 22.23.2 installations from their official Trixie source images into `/opt/devbox/runtimes/php/8.4` and `/opt/devbox/runtimes/node/22`. PHP-only, Node-only, combined, and no-Runtime Workspace variants ran successfully, and PHP and Node invoked each other in the combined image. PHP required relocated configuration and extension paths, while login shells required a `/etc/profile.d` path setup. The official PHP source image did not supply Composer, and this prototype did not exercise the later-decided Composer source, complete extension set, Node package-manager installation, materialized Base image, or host-matched non-root Sandbox user.

BuildKit accepted sequential `COPY --link` assembly but reused only the first selected Runtime's standalone layer in the combined image. The second Runtime produced a distinct layer with identical bundle contents; reversing the copy order reversed which Runtime was reused, and distinct top-level destination paths did not change the result. Docker reported a second unique Node layer of approximately 143.5 MB in the PHP-first combined image. Devbox accepts this duplication for the first release and treats reducing it as a later optimization; the deterministic Workspace fingerprint and verified-tag decisions remain unchanged.

## Integrated assembly evidence

A follow-up disposable prototype on 2026-08-02 completed the assembly gate on WSL2 `linux/amd64` with Docker Engine 29.3.1 and Buildx 0.31.1. It used PHP `8.4.24-cli-trixie@sha256:cf1d28d27b62f22fba23dd45dea795466d5252e68ae4de220f580f163921305e`, Node `22.23.2-trixie-slim@sha256:517aa41d78545cb1b8c67b13655b4c13ede1ee9df1da8aab54cd7434aefbcaf8`, Composer `2.10.2@sha256:4d71c3c2109c61d5415544264b59ad4087e4c5b7244481723664138fd36d5040`, digest-verified PhpRedis 6.3.0, and integrity-verified npm 12.0.2, Corepack 0.35.0, pnpm 11.18.0, and Yarn 1.22.22 packages. The complete PHP extension set, Composer, relocated PHP configuration and development tools, removed official-image helpers, Node package-manager flow, isolated paths, ownership boundaries, and unresolved-library scans all passed.

Base-only, Node-only, PHP-only, and Node-then-PHP Workspaces ran from the same materialized Base as a host-matched non-root user, exposed no unselected Runtime, and retained bidirectional PHP/Node invocation in the combined image. A Project-selected `pnpm@11.17.0` downloaded without a prompt, survived container stop and restart, and disappeared on replacement while the image-preloaded pnpm 11.18.0 remained. Invoking pnpm for a Project declaring npm failed the strict manager check. The writable Corepack subtree and otherwise immutable Node Runtime therefore require no layout change.

## Future Runtime ordering

If Python later joins the Runtime catalog, Runtime selection remains independent and the versioned assembly recipe defines one canonical total order: Node, then Python, then PHP. Every Workspace derives its layer order by preserving the relative positions of only its selected Runtimes in that total order, rather than enumerating Runtime combinations separately; unselected Runtimes are simply omitted. This ordering rule does not add Python to the first-release catalog.
