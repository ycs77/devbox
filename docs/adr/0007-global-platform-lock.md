# Share one Platform lock across all projects

Devbox keeps one user-scope Platform lock that maps each installed Base profile, Runtime release line, and Service release line to a single exact revision and immutable image digest shared by every project; AI Agents are intentionally outside this lock. Global `update` resolves every Runtime and Service release line already present in the lock, including installed entries not currently referenced by a project, then prepares the new artifacts and rebuilds every affected existing Workspace image before atomically activating the new lock generation; any resolution, build, or verification failure leaves the old generation active. Base changes remain explicit, and running Sandboxes remain unchanged until recreated. After activation Devbox retains no managed rollback generation, although Docker artifacts remain while referenced by an existing Sandbox. This prevents per-project patch drift, makes a successful update cover every previously built Toolchain combination, and avoids depending on the project registry, at the cost of longer updates and no built-in rollback after activation.

`update` is a global Platform operation rather than a Project configuration or application dependency operation. It never edits `devbox.yaml` or a Project's `config.yaml`, invokes Project package managers, or creates, starts, stops, or recreates Sandboxes.

`update` requires an existing valid `platform-lock.yaml`. If none exists, it fails without creating a Base-only lock and directs the user to bootstrap the Platform from a Project with `devbox sync` or `up`; an invalid lock remains a validation failure. If resolution finds every requested exact artifact already current, the command reports a successful no-op without preparing a candidate generation or rebuilding Workspace images.

The machine-owned Platform lock has an explicit integer `version: 1` schema field but no persisted generation identifier. In this decision, a generation means one complete Platform lock snapshot activated atomically, not a UUID or stored sequence number. Temporary candidate work may use an ephemeral unique ID, while Workspace image identity and freshness are established from content fingerprints rather than a second persistent generation identity.

An update keeps the candidate lock in memory, materializes and verifies any candidate Base image, builds and verifies every affected existing Workspace image from that candidate, and only then serializes it to a securely created, randomly named temporary file beside `platform-lock.yaml` before atomically renaming that file over the active lock. Devbox creates no host-side staging directory, persistent generation directory, backup lock, rollback metadata, or durable candidate manifest; candidate Base and Workspace images remain in Docker under content-derived local tags. Failure leaves the active lock untouched, while a stale temporary file or unreferenced Docker artifact from an interrupted attempt is a cleanup input.

Schema version 1 uses explicit `base` and `runtimes` mappings rather than a generic artifact list. `base` records the selected Base-profile identifier, its exact upstream `revision`, source `image`, immutable source `digest`, and the content-addressed local `image_id` of the materialized Base image; the stable `devbox-base:<image-id-hex>` tag is derived rather than stored. `runtimes` contains `php` and `node` mappings keyed by configured release line. Each Node entry records its exact Runtime revision, source image, and digest plus required nested `package_managers.npm`, `package_managers.corepack`, `package_managers.pnpm`, and `package_managers.yarn` mappings containing the exact npm-registry package revision and immutable registry integrity; the pnpm entry is the bundle's default Corepack Known Good Release, and Yarn is constrained to release line 1.x. Each PHP entry records the same PHP source fields plus one required nested `composer` mapping containing the exact compatible Composer revision, official source image, and immutable digest selected independently for that PHP release line, and one required nested `extensions.redis` mapping containing the exact PhpRedis release and immutable PECL archive digest; Devbox derives the official PECL source location from the release. Empty Runtime mappings are valid, installed but currently unreferenced release lines remain present, and the initial schema contains no placeholder Service section.

For the current Project, `devbox sync` takes the selected Toolchain from the Resolved configuration and chooses one applicable Platform lock snapshot before selecting an image. It uses the active lock when every required Base and Runtime entry is present; otherwise it resolves only the missing required entries into an in-memory candidate that extends the active lock, or into the first candidate lock when no active file exists. Sync never refreshes an already locked revision or digest; changing existing entries remains the responsibility of the global Platform or explicit Base update operations. It computes the one desired Workspace fingerprint from that Toolchain and applicable lock snapshot, then asks the internal Build module to reuse the matching stable tag or to build and verify the image before assigning it. A candidate lock becomes active only after that desired image is ready, and generated Compose is written last. Sync never selects a merely compatible or most-recent image and keeps no Project image record, latest pointer, or Workspace registry.

Before reusing or building a Workspace image, Devbox requires the derived Base tag to resolve to the exact locked local image ID. A missing tag, missing image, or mismatched ID is an operational failure with an instruction to run `devbox update --base`; Sync never rematerializes or repairs an active Base entry because a fresh native-package resolution would create a different Platform input.

Concurrent Project operations use resource-scoped advisory locks beneath the shared user-scope lifecycle lock. A Sync whose required entries already exist in the active Platform lock needs no Platform mutation lock. A Sync that must add entries takes the exclusive Platform mutation lock, rereads the active lock after acquisition, and keeps that lock through candidate image preparation and atomic activation so another Project cannot publish a candidate derived from a stale snapshot. Every Build takes an exclusive lock keyed by the desired fingerprint and rechecks the stable tag after acquisition; Projects requesting the same image therefore share the winner's verified tag instead of building or assigning it concurrently, while different fingerprints may build in parallel. Locks are always acquired in the order user-scope lifecycle, Project when applicable, Platform mutation when applicable, then fingerprint, and released in reverse order.

If `platform-lock.yaml` does not exist, Sync treats the Platform lock as not yet created and atomically creates schema version 1 with the entries required by the current Project only after its Workspace image has built and verified. Devbox cannot reliably distinguish first use from manual deletion, so both cases follow this bootstrap path and other Projects add their missing entries through later Sync operations. An existing but invalid Platform lock instead fails validation and is never repaired automatically.

The first bootstrap candidate also materializes and verifies its Base image before building the current Project's Workspace image; the Base tag and candidate lock become authoritative only through the same successful activation boundary.

During sync, a candidate containing newly required entries becomes active only after the required Workspace image has built and verified successfully. That verified lock and image remain valid if the later per-Project Compose write fails; the next sync retries only the remaining derived work instead of rolling back globally usable state.

Build, publication, and activation failures are forward-only and retryable rather than simulated as one transaction. A resolution, build, verification, or stable-tag assignment failure leaves the active Platform lock and retained Compose unchanged and never publishes an unverified stable tag. If a verified stable tag exists but candidate-lock activation fails, the active lock and Compose still remain unchanged; the tag is safe to reuse if a later retry resolves the same fingerprint and otherwise remains an unreferenced cleanup input. A Compose failure after successful candidate activation does not roll back the newly valid lock or tag. Temporary or untagged candidate artifacts left by any interrupted attempt carry no readiness meaning and remain cleanup inputs.
