# Share one Installed Runtime set across Project Sandboxes

ADR-0034 renames the active user-scope concept to Configured Runtime set because explicit configuration, resolution, and build stages may be incomplete, and supersedes automatic expansion by a Project selection: `config` may select only a Runtime already present in Global configuration and directs the user to `config -g` otherwise. User-scope ownership, explicit proactive addition, guarded removal, and common Workspace inclusion remain in force.

Devbox keeps one Sandbox container per Project but uses one common immutable Workspace image assembled from the Base profile and the Configured Runtime set. A Project's Toolchain still selects zero or one release line per Runtime family, while the Configured Runtime set may contain additional release lines required by other Projects; Runtime selection controls the Project's supported command resolution rather than its container boundary. This retains Project-scoped workspace, process, network, writable-layer, and lifecycle isolation without adopting a single shared container.

Users add or remove Configured Runtime entries only through explicit Global configuration. Local `config` may select only an already configured entry, and removal from Global configuration is rejected while any registered Project, including a Missing-root Project registration, still selects it. The set manages only Runtime families and release lines; family recipes own Composer, PHP extensions, Node package managers, and other curated tools.

The removal guard evaluates registered Projects' Local selections rather than Sandbox actual state. A running or stopped Sandbox that still uses an older Workspace image containing the Runtime does not block removal from the Configured Runtime set: its immutable container image reference preserves that actual state independently until later replacement, teardown, or cleanup. This keeps Global desired-state changes separate from stale container lifecycle without weakening the guard for Missing-root Project registrations.

The Workspace image and explicitly modeled user-scope resources such as Agent homes may be shared across Project containers. Project workspaces, container writable layers, processes, networks, and lifecycle state are never shared. Changing the Configured Runtime set requires later explicit `update` and `build` stages before the common image reflects it, an accepted trade-off for preparing each configured Runtime once per user.
