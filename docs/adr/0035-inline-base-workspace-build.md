# Build Base layers inside the Workspace image

Devbox removes the separately materialized local Base image, its `devbox-base:<image-id>` tag, and the Base local `image_id` from Platform-lock schema version 1. The Base profile remains Devbox-selected package data and the shared Runtime ABI, while the Platform lock records its exact upstream source revision and digest plus the exact curated native-package plan needed by Build. Ordinary `update` resolves and atomically writes those Base inputs together with the Configured Runtime set without invoking Docker.

For Ubuntu Noble, that plan locks the `ubuntu:24.04` source digest, one official Ubuntu snapshot timestamp, and the ordered Devbox-curated top-level package names. It does not enumerate package versions or the transitive dependency closure: the `apt` contained in the digest-pinned Base resolves them from the immutable snapshot during Build, avoiding both a second apt solver in the CLI and unrebuildable version pins against the moving regular archive. Ubuntu documents the snapshot service as its supported reproducibility mechanism: <https://documentation.ubuntu.com/server/how-to/software/snapshot-service/>.

The public `build` command consumes the complete lock and generates the Base stages at the beginning of the same machine-owned Workspace Dockerfile before adding configured Runtime stages and building `devbox-workspace:latest`. A bootstrap `build` resolves and creates the same complete lock when none exists. This supersedes ADR-0004's separate Base materialization, ADR-0008's `update --base` lifecycle, and the Base-image identity and cleanup portions of ADR-0007 and ADR-0016, accepting repeated BuildKit evaluation of cached Base stages in exchange for one image pipeline and a lock that `update` can manage without Docker side effects. ADR-0041 keeps Configured Agents and Devbox-added Node global tools out of this image.
