# Generate Compose outside the project

Devbox manages a Sandbox and any future Services by generating an internal Compose definition in Devbox-owned user data and invoking Docker Compose. The initial release ships no Service catalog and generates Sandbox-only definitions, while retaining Compose as the lifecycle and networking foundation for later curated Services. This keeps projects free of required Docker configuration and avoids rebuilding Compose semantics around individual `docker run` calls; generated Compose is an implementation detail, not a user extension surface.

The generated definition for a Project is the machine-owned `compose.yaml` stored beside that Project's Local configuration at `~/.devbox/projects/<mirrored-project-root>/compose.yaml`. Co-location does not make it a supported editing or extension interface, and only the neighboring `config.yaml` registers the Project.

The retained file represents the most recently synchronized desired Sandbox definition rather than a continuously refreshed view. A successful explicit `devbox sync`, or the same synchronization invoked automatically by `up`, deterministically renders it and atomically rewrites it only when its contents differ; Devbox keeps no dirty flag, input-fingerprint sidecar, or Compose freshness metadata. Configuration and Platform changes take effect in this definition through the next sync, while `down`, `shell`, and `exec` read the retained file without regenerating it.

Sync writes Compose last. If rendering or its atomic write fails, the command fails and retains the previous `compose.yaml`, while already validated Local configuration and any verified Platform lock or Workspace image preparation remain committed for a later retry.

Generated Compose marks every Sandbox container and Project-scoped Compose resource with Devbox ownership and Project identity labels so cleanup can discover them without a host-side registry. Before deleting anything, `devbox cleanup` inspects every Devbox-owned Sandbox container and aborts the entire operation if any is running. Otherwise it removes the stopped Sandbox containers and their Project-scoped rebuildable Compose resources, then cleans eligible temporary files and Workspace image tags while retaining every Project registration, generated `compose.yaml`, and Docker volume. It rechecks each container immediately before removal and never forces removal; a container that starts after preflight causes the command to fail rather than deleting it. The preview warns that each removed container's writable layer, including its installed AI Agent executable, will be lost and that the next `up` recreates it with the then-current Agent. Devbox exposes no `--stopped` mode and no separate `prune` command or alias.

Cleanup always builds and displays one plan containing running blockers, stopped Sandboxes and networks selected for removal, disposable temporary files, and eligible Workspace image tags. In an interactive terminal it requires one confirmation before applying that plan; outside an interactive terminal it fails unless the user passes `--yes`, which bypasses only the prompt and never the running-Sandbox or state-recheck protections. `--dry-run` displays the same plan without prompting or deleting anything.

Project-local `stop` and `down` operate only from the retained `compose.yaml` and never invoke Sync. `stop` stops the Sandbox while preserving its container, writable layer, network, and volumes for a later restart. `down` stops and removes the Sandbox container and its Project-scoped rebuildable Compose network while retaining the Project registration, generated Compose definition, Workspace image tag, and every volume; it reports that the container writable layer and installed AI Agent executable are discarded.
