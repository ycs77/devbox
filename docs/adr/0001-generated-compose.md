# Generate Compose outside the project

Devbox manages a Sandbox and any future Services by generating an internal Compose definition in Devbox-owned user data and invoking Docker Compose. The initial release ships no Service catalog and generates Sandbox-only definitions, while retaining Compose as the lifecycle and networking foundation for later curated Services. This keeps projects free of required Docker configuration and avoids rebuilding Compose semantics around individual `docker run` calls; generated Compose is an implementation detail, not a user extension surface.

The generated definition for a Project is the machine-owned `compose.yaml` stored beside that Project's Local configuration at `~/.devbox/projects/<mirrored-project-root>/compose.yaml`. Co-location does not make it a supported editing or extension interface, and only the neighboring `config.yaml` registers the Project.

The retained file represents the most recently synchronized desired Sandbox definition rather than a continuously refreshed view. A successful explicit `devbox sync`, or the same synchronization invoked automatically by `up`, deterministically renders it and atomically rewrites it only when its contents differ; Devbox keeps no dirty flag, input-fingerprint sidecar, or Compose freshness metadata. Configuration and Platform changes take effect in this definition through the next sync, while `down`, `sh`, and `exec` read the retained file without regenerating it.

`devbox sh` is a Project-local interactive attachment to an existing running and ready Sandbox. The short command name is an ergonomic shorthand and intentionally opens `/bin/bash --login` rather than POSIX `/bin/sh`. It reads the retained Compose definition without invoking Sync or any Sandbox lifecycle operation; if no Sandbox exists, it is stopped, or it is not ready, the command fails with an actionable instruction to run or finish `devbox up`. In an interactive terminal it uses Compose exec with stdin and a TTY, starting in the Project workspace and inheriting the Sandbox's configured user and environment. Outside an interactive terminal it fails and directs command execution to `devbox exec`. Terminal signals and the shell's final exit status are propagated to the caller.

`devbox exec <command> [args...]` is the non-starting command-execution counterpart. It has the same running-and-ready requirement, retained-Compose behavior, Project-workspace working directory, Sandbox user and environment, and no-Sync/no-lifecycle boundary as `sh`. Devbox passes the command and each argument directly to Compose exec without a shell, interpolation, pipe, redirect, or combined command string; callers that need shell syntax invoke `bash -lc` explicitly. The command inherits stdin, stdout, and stderr, allocates a TTY only when the calling environment is interactive, forwards signals, and exits with the executed process's status. Invoking `exec` without a command is a usage error.

A successful Sync always supersedes the prior retained image reference with the newly desired stable Workspace tag, even when an existing running or stopped Sandbox container still uses the old image. The retained Compose definition is desired state; the container and its immutable image reference are actual state, and their temporary difference is not a dirty condition. Sync never recreates, stops, starts, or mutates that container and stores no prior image pointer or parallel actual-state file. During the difference, the retained Compose definition protects the new tag from cleanup and the existing container protects the old image.

Sync writes Compose last. If rendering or its atomic write fails, the command fails and retains the previous `compose.yaml`, while already validated Local configuration and any verified Platform lock or Workspace image preparation remain committed for a later retry.

Generated Compose marks every Sandbox container and Project-scoped Compose resource with Devbox ownership and Project identity labels so cleanup can discover them without a host-side registry. Before deleting anything, `devbox cleanup` inspects every Devbox-owned Sandbox container and aborts the entire operation if any is running. Otherwise it removes the stopped Sandbox containers and their Project-scoped rebuildable Compose resources, then cleans eligible temporary files and Base or Workspace image tags while retaining every Project registration, generated `compose.yaml`, and Docker volume. It rechecks each container immediately before removal and never forces removal; a container that starts after preflight causes the command to fail rather than deleting it. The preview warns that each removed container's writable layer, including its installed AI Agent executable, will be lost and that the next `up` recreates it with the then-current Agent. Devbox exposes no `--stopped` mode and no separate `prune` command or alias.

Cleanup always builds and displays one plan containing running blockers, stopped Sandboxes and networks selected for removal, disposable temporary files, and eligible Base or Workspace image tags. In an interactive terminal it requires one confirmation before applying that plan; outside an interactive terminal it fails unless the user passes `--yes`, which bypasses only the prompt and never the running-Sandbox or state-recheck protections. `--dry-run` displays the same plan without prompting or deleting anything.

After completing full Sync, `up` first checks the Project's existing Sandbox container. A running Sandbox is always left unchanged: `up` performs no Compose lifecycle work and reports that the latest retained Compose definition has not been applied. With no existing Sandbox, `up` creates and starts one from the latest retained definition. A stopped Sandbox is restarted unchanged when applying that definition would not require container replacement. When replacement would be required, interactive `up` asks before starting anything and defaults to No: Yes removes only the stopped Sandbox container and its writable layer, retains its Project-scoped network and every volume, then creates and starts the desired container; No starts the old container without recreation and warns that its old image, ports, and other creation-time settings remain in effect. Outside an interactive terminal, `up` never waits for input and follows the same non-recreating No path with the warning. This choice is evaluated from desired and actual state at invocation time and stores no dirty marker or prior Compose file. The initial CLI exposes no separate `recreate` command or `up --recreate`; users can force a fresh container non-interactively with `down` followed by `up`, which also recreates the rebuildable network.

Sandbox start and confirmed replacement failures follow the same forward-only rule. Failure to start an old stopped container leaves that container and its writable layer intact. On the Yes path, Sync has already prepared the desired image and retained Compose before Devbox attempts removal; failure to remove the old container stops the operation without attempting replacement. Once removal succeeds, its writable layer cannot be restored: if creation, Agent installation, readiness, or start then fails, Devbox never presents a newly reconstructed old container as rollback. It retains the Project registration, latest Compose definition, Project-scoped network, every volume, and the Docker state that actually remains, reports whether a failed new container or no container exists, and lets the next `up` retry from that observed state.

Project-local lifecycle operations take a shared user-scope lifecycle lock and an exclusive lock for their Project, allowing different Projects to run concurrently while serializing `sync`, `up`, `stop`, `down`, and `rm` for the same Project. Global Platform or Base updates and `cleanup` take the user-scope lifecycle lock exclusively so candidate activation, global inspection, and deletion cannot race Project-local publication or container changes. These are OS advisory locks used only for live process coordination: their files carry no generation or domain state and the OS releases ownership when a process exits. When a required lock is unavailable, the command reports what resource it is waiting for and waits until acquisition rather than failing or imposing a fixed timeout; cancellation while waiting changes nothing. After acquisition it rereads every state input protected by that lock rather than continuing from a pre-lock observation.

Project-local `stop` and `down` operate only from the retained `compose.yaml` and never invoke Sync. `stop` stops the Sandbox while preserving its container, writable layer, network, and volumes for a later restart. `down` stops and removes the Sandbox container and its Project-scoped rebuildable Compose network while retaining the Project registration, generated Compose definition, Workspace image tag, and every volume; it reports that the container writable layer and installed AI Agent executable are discarded.
