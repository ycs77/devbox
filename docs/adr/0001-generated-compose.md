# Generate Compose outside the project

ADR-0034 supersedes this decision's Compose regeneration through configuration or shared reconciliation: only `up` now renders and atomically retains the current Project definition before invoking Compose, while `stop`, `down`, `sh`, `exec`, and `logs` use the last retained file. ADR-0032 supersedes references to fingerprinted Workspace tags, ADR-0041 defines current per-Sandbox Agent installation, and ADR-0042 supersedes the neighboring Local `config.yaml` as registration truth. The Project registry now owns registration while Compose remains machine-owned state outside the Project.

Devbox manages a Sandbox and any future Services by generating an internal Compose definition in Devbox-owned user data and invoking Docker Compose. The initial release ships no Service catalog and generates Sandbox-only definitions, while retaining Compose as the lifecycle and networking foundation for later curated Services. This keeps projects free of required Docker configuration and avoids rebuilding Compose semantics around individual `docker run` calls; generated Compose is an implementation detail, not a user extension surface.

The generated definition for a Project is the machine-owned `compose.yaml` stored beside that Project's Local configuration in the flat state directory assigned by the Project registry under `~/.devbox/projects/`. Co-location does not make it a supported editing or extension interface, and only the matching `projects.yaml` entry registers the Project.

The retained file is the most recently published desired Sandbox definition rather than a continuously refreshed view. Only `up` renders it from the current Project registry, Global configuration, Local configuration, and host inputs, then atomically rewrites it only when the bytes differ before invoking Compose; Devbox keeps no dirty flag, input fingerprint, or freshness metadata. `stop`, `down`, `sh`, `exec`, and `logs` read the retained file without regenerating it.

Generated Compose is derived state, so Devbox never migrates it field by field. `up` renders the complete current definition and keeps the previous file until the new bytes are ready for the final atomic replacement.

The single retained definition keeps Devbox metadata inside Compose's top-level `x-devbox` extension rather than a companion file or Compose's reserved top-level `version` field. `x-devbox` carries `version: 1`, the exact Project root, fixed Compose name, and fixed Sandbox service name; Devbox validates those values against the Project registry and the standard Compose `name`, service, and ownership labels before invoking Compose. Mutable Sandbox desired state remains in standard Compose fields, so one atomic replacement publishes the complete definition. During pre-release development Devbox supports only this current version-1 envelope and implements no older-shape reader or migration path; an unsupported version, malformed definition, or identity mismatch fails closed without invoking Compose or rewriting the only retained description of the existing Sandbox.

`devbox sh` is a Project-local interactive attachment that intentionally opens `/bin/bash --login` rather than POSIX `/bin/sh`. It reads the retained Compose definition and invokes Compose exec directly without regeneration, other lifecycle work, or a prior Devbox check for container existence, running state, bootstrap completion, or readiness; Compose's own error and exit status are returned unchanged. In an interactive terminal it attaches stdin and a TTY, starts in the Project workspace, and uses the Sandbox's configured user and environment. Outside an interactive terminal it is a usage error directing command execution to `devbox exec`. Terminal signals and the shell's final exit status propagate through Compose.

`devbox exec <command> [args...]` is the non-starting command-execution counterpart. It has the same retained-Compose behavior, Project-workspace working directory, Sandbox user and environment, direct Compose invocation, and no-precheck/no-regeneration/no-lifecycle boundary as `sh`. Devbox passes the command and each argument directly to Compose exec without a shell, interpolation, pipe, redirect, or combined command string; callers that need shell syntax invoke `bash -lc` explicitly. The command inherits stdin, stdout, and stderr, allocates a TTY only when the calling environment is interactive, forwards signals, and returns Compose or the executed process's status unchanged. Invoking `exec` without a command is a usage error.

`devbox logs [--follow]` is the Project-local diagnostic counterpart for detached startup. It reads the retained Compose definition and directly invokes `docker compose logs`, adding `--follow` only when requested, without a container-state precheck, Compose regeneration, or lifecycle action. Compose output, errors, signals, and exit status pass through unchanged. The initial interface accepts no service selection, tail count, timestamp, or other Compose-log option.

Every retained Compose definition references the single mutable `devbox-workspace:latest` tag. A later `build` may move that tag without changing retained Compose, while an existing running or stopped Sandbox container remains attached to its prior immutable image; this desired-versus-actual difference is not a dirty condition and Devbox stores no prior image pointer or parallel actual-state file. Cleanup preserves `latest`, and each existing container protects the exact older image it still uses.

`up` publishes Compose before invoking `docker compose up -d`. If rendering or the atomic write fails, the operation fails without invoking Compose and retains the previous `compose.yaml`; if Compose later fails, the newly published desired definition remains for an explicit retry.

Generated Compose marks every Sandbox container and Project-scoped Compose resource with Devbox ownership and Project identity labels so Cleanup discovers Docker resources from Docker rather than treating the Project registry as a Docker-resource inventory. Before deleting anything, `devbox cleanup` inspects every Devbox-owned Sandbox container and aborts the entire operation if any is running. Otherwise it removes the stopped Sandbox containers and their Project-scoped rebuildable Compose resources, then cleans eligible temporary files and unreferenced old Workspace images while retaining `devbox-workspace:latest`, every Project registration, generated `compose.yaml`, and Docker volume. It rechecks each container immediately before removal and never forces removal; a container that starts after preflight causes the command to fail rather than deleting it.

Cleanup always builds and displays one plan containing running blockers, stopped Sandboxes and networks selected for removal, disposable temporary files, and eligible unreferenced old Workspace images. In an interactive terminal it requires one confirmation before applying that plan; outside an interactive terminal it fails unless the user passes `--yes`, which bypasses only the prompt and never the running-Sandbox or state-recheck protections. `--dry-run` displays the same plan without prompting or deleting anything.

A Cleanup plan may include an old Workspace image that is still referenced only by a stopped Sandbox container already selected in that plan. The plan displays that dependency before confirmation, removes and rechecks the stopped container first, then removes the image only if a fresh inspection shows that no container references it. A container that starts or a new reference that appears after planning makes the affected operation fail safely; users do not need a second Cleanup invocation merely because the image became unreferenced through the confirmed container removal.

After atomically retaining the current Project's Compose definition, `up` directly invokes `docker compose up -d` without pre-inspecting the existing Sandbox, calculating replacement requirements, adding `--no-recreate`, or presenting a Devbox replacement prompt. Compose alone decides whether to leave a running container, start a stopped one, create a missing one, or recreate one whose image or definition changed. Ordinary `up` may therefore discard an existing container writable layer and its installed tools without a separate Devbox confirmation; users who need to inspect or preserve that state do so before invoking `up`.

`up` returns Compose's exit status and treats exit `0` as complete command success. It does not wait for entrypoint preflight, bootstrap, a completion marker, a long-lived process, or Docker health state. A nonzero Compose exit fails the command without Devbox rollback, while an entrypoint or installer failure after detached startup does not retroactively change a successful `up`; users diagnose asynchronous container output through Compose logs and retry with another explicit lifecycle command.


Project-local lifecycle and configuration operations that do not change Project registration take a shared user-scope lifecycle lock and an exclusive lock for their Project, allowing different Projects to run concurrently while serializing `config`, `up`, `stop`, and `down` for the same Project. `init`, `rm`, `cleanup --missing-projects`, `config -g`, `update`, `build`, and other Cleanup modes take the user-scope lifecycle lock exclusively because they mutate the Project registry or other global desired, derived, or disposable state; `rm` additionally holds its Project lock. These are OS advisory locks used only for live process coordination: their files carry no generation or domain state and the OS releases ownership when a process exits. When a required lock is unavailable, the command reports what resource it is waiting for and waits until acquisition rather than failing or imposing a fixed timeout; cancellation while waiting changes nothing. After acquisition it rereads every state input protected by that lock rather than continuing from a pre-lock observation.

`build` also holds the user-scope lifecycle lock exclusively for its complete operation, including Platform-lock bootstrap when absent, Workspace-context regeneration, Docker build, and publication of `devbox-workspace:latest`. This deliberately blocks Project operations for the duration so no `up` races mutable-tag publication and no global mutation or Cleanup changes or deletes state Build is consuming.

Each outer operation owns its complete lock lifetime and passes only the opaque lease capabilities required by inner state or lifecycle modules; inner modules never acquire locks themselves. Only the production lock adapter constructs a lease, consumers reject a lease for another Project or one already released, and protected state is first read after acquisition.

The production lock adapter recognizes only the user-scope lifecycle scope and Project scopes. It starts one resolved compatible internal `devbox-host` child from Devbox's independently versioned platform package for each requested scope. A versioned JSON Lines protocol on stdin and stdout carries acquire, ready, error, and release messages; stdout contains protocol messages only, helper diagnostics use stderr, and no daemon or socket exists. The helper keeps each shared or exclusive kernel advisory-lock file descriptor open after reporting ready and releases it when instructed, when stdin reaches EOF, or when the helper exits; it contains no Project, Build, or CLI presentation policy. Vitest replaces this adapter for module tests, while focused integration tests exercise the real helper's contention, malformed-protocol, cancellation, parent-crash, and release behavior.

Before reading protected state, each outer operation declares its complete required lock set in one acquisition request. The lock adapter always acquires the user-scope lifecycle lock first, then any Project locks ordered by canonical Project identity, and returns one opaque composite lease only after every scope is held; release is in reverse order. Inner modules may validate or consume capabilities from that lease but never acquire an additional scope, upgrade a held mode, or choose an acquisition order. Cancellation or acquisition failure releases the already acquired prefix and exposes no lease. There are no separate Platform-mutation, Workspace-context, or Compose locks: exclusive lifecycle ownership protects every Global operation and shared lifecycle plus exclusive Project ownership protects retained Compose and that Project's Docker lifecycle.

Project-local `stop` and `down` operate only from the retained `compose.yaml` and never regenerate it. `stop` stops the Sandbox while preserving its container, writable layer, network, and volumes for a later restart. `down` stops and removes the Sandbox container and its Project-scoped rebuildable Compose network while retaining the Project registration, generated Compose definition, `devbox-workspace:latest`, and every volume; it reports that the container writable layer and installed Node tools and AI Agent executables are discarded.
