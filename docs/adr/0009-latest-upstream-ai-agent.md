# Install the latest AI Agent when creating a Sandbox

The initial AI Agent catalog supports Claude Code and Codex, and Codex inclusion is not gated on a separate packaging or authentication prototype. AI Agent executables are intentionally excluded from the Platform lock and Workspace images so their fast update cadence does not force Base or Runtime image rebuilds. When a selected Agent executable is absent, the Sandbox entrypoint installs whatever release the official upstream installation path resolves as latest into that Sandbox's writable container layer, outside the shared Agent home; for Claude Code, that path is `curl -fsSL https://claude.ai/install.sh | bash`. The Sandbox becomes ready only after installation succeeds.

A newly created Sandbox therefore obtains the then-current Agent, while stopping and restarting the same container reuses its existing installation and recreating it installs latest again. Devbox maintains no shared Agent bundle, Docker `:current` pointer, Agent generation, or host-side Agent version registry, and different Sandboxes may deliberately contain different Agent versions. This decouples frequent Agent changes from Workspace image assembly and avoids Agent-driven image rebuilds, at the accepted cost of network-dependent first startup, weaker cross-Project version consistency, and no pre-activation verification across every Project.

## Sandbox bootstrap evidence

On 2026-08-03, a disposable production-shaped prototype on WSL2 `linux/amd64` started from a Workspace-shaped image containing no Agent executable, aligned the Sandbox user to the host identity `1000:1000`, and invoked Claude Code's official native installer only after dropping root. The installer resolved Claude Code 2.1.220, placed its launcher and version payload under the Sandbox user's `~/.local`, and produced no root-owned artifact in the controlled Agent, cache, or Project writable paths. Stopping and restarting the same container reused that installation; removing and recreating the container from the Agent-free image ran the official installer again while retaining the separately mounted Agent home and Project workspace.

The first readiness probe also showed that the launcher can become executable before the upstream installer has fully completed. Sandbox readiness must therefore depend on an explicit post-install completion condition, not merely on existence or executability of the Agent launcher. The corrected probe waited for completion and passed. This evidence clarifies the readiness implementation and reveals no contradiction in the accepted installation lifecycle; it does not establish Codex behavior or any platform beyond the exercised WSL2 host.
