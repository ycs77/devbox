# Install the latest AI Agent when creating a Sandbox

ADR-0030 supersedes per-Project Agent selection, ADR-0034 names the user-scope Configured Agent set, and ADR-0041 restores and replaces this decision's first-start installation lifecycle. The current contract installs every Configured Agent independently of Selected Runtimes, bootstraps applicable Node global tools separately, uses one atomic completion marker, and applies to every Project Sandbox.

The initial Agent catalog supports Claude Code and Codex. AI Agent executables are intentionally excluded from the Platform lock and Workspace images so their fast update cadence does not force Base or Runtime image rebuilds. Sandbox bootstrap installs whatever release each official Runtime-independent path resolves as latest into that Sandbox's writable container layer, outside the shared Agent home: Claude Code uses `curl -fsSL https://claude.ai/install.sh | bash`, and Codex uses `curl -fsSL https://chatgpt.com/codex/install.sh | sh`. Both current official installers publish their launcher under the Sandbox user's `~/.local/bin` and update a shell profile; Devbox preserves that behavior rather than adding the directory to the Compose environment. Installer exit `0` is the complete installation-success contract; Devbox performs no command lookup, version check, or Agent smoke test.

A newly created Sandbox therefore obtains the then-current Agent, while stopping and restarting the same container reuses its existing installation and recreating it installs latest again. Devbox maintains no shared Agent bundle, Docker `:current` pointer, Agent generation, or host-side Agent version registry, and different Sandboxes may deliberately contain different Agent versions. This decouples frequent Agent changes from Workspace image assembly and avoids Agent-driven image rebuilds, at the accepted cost of network-dependent first startup, weaker cross-Project version consistency, and no pre-activation verification across every Project.

## Sandbox bootstrap evidence

On 2026-08-03, a disposable production-shaped prototype on WSL2 `linux/amd64` started from a Workspace-shaped image containing no Agent executable, aligned the Sandbox user to the host identity `1000:1000`, and invoked Claude Code's official native installer only after dropping root. The installer resolved Claude Code 2.1.220, placed its launcher and version payload under the Sandbox user's `~/.local`, and produced no root-owned artifact in the controlled Agent, cache, or Project writable paths. Stopping and restarting the same container reused that installation; removing and recreating the container from the Agent-free image ran the official installer again while retaining the separately mounted Agent home and Project workspace.

The first bootstrap probe also showed that the launcher can become executable before the upstream installer has fully completed. The completion marker must therefore follow successful installer exit rather than launcher existence. The corrected probe waited for installer completion and passed. This evidence supports the marker rule but does not create Sandbox readiness or `up` waiting semantics, and it does not establish Codex behavior or any platform beyond the exercised WSL2 host.
