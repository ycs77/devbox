# Keep the initial CLI explicit and human-oriented

The initial public command surface is limited to Project-local `init`, `config`, `sync`, `up`, `sh`, `exec`, `stop`, `down`, and `rm`, plus global `update` and `cleanup`. Devbox adds no speculative status, list, logs, build, prune, recreate, Agent-authentication, Agent-reset, or generic volume-management command. New commands require a concrete first-release need rather than a placeholder namespace.

`init` registers the current existing directory as a Project. Every other Project-local command requires that exact directory to be registered and fails with an actionable `devbox init` instruction rather than registering implicitly; Missing-root registrations remain addressable only through `cleanup --missing-projects`. Global commands work independently of the current directory. Commands whose target state already holds are successful no-ops: this includes `stop` with no running container, `down` with no remaining container or rebuildable network, and `cleanup` with nothing eligible, while `up` retains its separately defined Sync and running-Sandbox behavior.

Exit status `0` means success, including a no-op or an explicit No at a confirmation; `1` means Devbox validation or operational failure; `2` means CLI usage error; and interruption by Ctrl-C returns `130`. `sh` and `exec` instead propagate the attached child process's exit status. The initial CLI exposes human-readable output only: normal results and plans use stdout, warnings and Devbox errors use stderr, and errors state the observed condition plus the next supported action. For `sh` and `exec`, child stdout and stderr remain unmodified and Devbox diagnostics use stderr. Devbox provides no `--json`, `--quiet`, or stable prose-parsing contract in the initial release.
