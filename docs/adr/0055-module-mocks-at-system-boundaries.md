# Prefer module mocks at initialization and configuration system boundaries

For initialization and configuration flows, Lucas prefers direct imports and `vi.mock` of terminal-interaction and host-process adapters over dependency parameters added solely for tests. This is an explicit style preference departing from the TDD skill's default DI recommendation, not a requirement to eliminate DI: `root`, `devboxHome`, `signal`, and genuine operational inputs remain appropriate parameters. All other TDD principles remain in force, including agreed public test seams, one behavioural Red → Green slice at a time for interface changes, and real internal collaborators.

Only system-boundary adapters may be mocked: terminal interaction, external processes, and filesystem failure injection with `node:fs/promises` and memfs. Publication, Project-registry, and command-lock logic remain real. Boundary arguments and whether interaction occurs may be observed when they represent user-visible behaviour, such as confirmation details or no prompt when a required lock is busy; internal call order and incidental collaborator calls are not contracts.

The main sources of unnecessary complexity are the parallel interactive/programmatic input paths and exposed publication state, not DI itself. Remove the test-only `initial*`/`next*` paths, use named interaction functions with explicit I/O options, and encapsulate raw publication state while preserving validation, configuration snapshots, semantic no-change decisions, user-owned YAML bytes, and rollback behaviour. Removing the parallel paths is a separate simplification enabled by driving tests through interaction; it does not technically require module mocking.

## Trade-off and scope

DI with a fake prompter could also remove the parallel input paths. Module mocks were chosen for Lucas's preferred direct-import style despite their dependence on import paths and their setup/reset cost in `test/project/index.test.ts` and the four tests using initialization as setup: filesystem, lifecycle, generated artifacts, and Compose smoke. Do not compensate with a generic mock framework, module-level mutable I/O state, or mocks of internal collaborators.

S0 (#48) implements the named terminal functions with per-call `signal`/`input`/`output` options, direct terminal and host imports in Project operations, and system-boundary module mocks in all five operation/setup test files. CLI scope selection and removal confirmation use the same named terminal functions; removal retains its narrow confirmation callback. Each test file owns and resets its boundary mocks; publication, registry, and locks remain real.

S1 (#49) makes initialization a single `InitializeProjectOptions` object containing only `root`, `devboxHome`, and `signal`. Initialization always collects configuration through the named interaction functions, uses the packaged catalog, and validates the returned configuration before publication. All five operation/setup test files supply initialization data through their own resettable terminal module mocks. Registered Projects still return before reading configuration, prompting, or publishing definitions.

Path construction, Sandbox identity/name encoding and allocation now live in `src/project/registry.ts`, including `devboxPaths` used by Workspace builds. Callers import from that module directly; the old Project-operation re-exports do not exist. Registry schema, collision rules, publication state and command locks are unchanged.

S2 (#50) makes Global configuration a single `ConfigureGlobalOptions` object containing only `devboxHome` and `signal`. Global answers and per-Project Node replacements come from the named interaction functions and remain validated. Global configuration is observed before the registry; all registered Project locks are acquired before editing, including retained Missing-root registrations.

Each operation now owns a `ProjectPublication` instance. Its domain reads retain raw file snapshots privately at the original observation points, not at publish time. Operations pass desired configuration, semantic change decisions and registry data, never `FileState`, previous bytes or prepared writes. Initialization still prepares its definition before confirmation; Global and Local prepare after confirmation. Publication retains all-file staging, content-identical definition suppression, reverse rollback and original errors. Unchanged user-owned YAML is not serialized for writing, preserving comments and original bytes. init, Global and Local all use this interface; removal and Sandbox startup only adapt their plain-text read.

S3 (#51) makes Local configuration a single `ConfigureLocalOptions` object containing only `root`, `devboxHome`, and `signal`. All three operations now obtain configuration exclusively through the named interaction functions and use the packaged catalog; no `initial*`/`next*` data inputs, test-only dependencies, factory object, obsolete helper or compatibility re-export remains. Local reads only the registry, Global configuration and the current Project's Local configuration, even if another registered Project has invalid Local YAML.

Local confirmation, validation, cancellation, lock scope and publication snapshots are unchanged. An accepted unchanged form still refreshes the current definition, without rewriting semantically unchanged user YAML or content-identical Compose. The now-unused scope-dependent missing-configuration helper is removed; the remaining missing-Global error is emitted at the same point with the same text. Required registry reads are not generalized into an all-Project loader.

Issue #47 tracks final integration review of S0–S3; implementation does not imply approval to merge or deploy. The completed #42 / PR #46 delivery remains historical fact. ADR-0045's command-lock and ADR-0049's configuration/publication contracts are unchanged.
