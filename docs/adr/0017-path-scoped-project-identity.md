# Treat each project root as a distinct Project

ADR-0042 supersedes this decision's registration storage and unregister commit point: the machine-owned Project registry is the sole registration authority, while Local `config.yaml` contains no duplicate Project root. Exact path-scoped Project identity, Missing-root classification, and explicit removal remain in force.

Devbox identifies a Project by the existing current working directory reported by the operating system rather than Git remote, repository lineage, or extra filesystem alias detection. `devbox init` uses exactly the directory in which it is invoked as the root and never climbs to a Git top-level directory; separate subdirectories, clones, and worktrees therefore remain eligible for independent Local configuration, ports, Services, Agent state, and Sandbox lifecycle, while non-Git directories use the same model. Moving a root creates a new Project that must be initialized independently; Devbox neither infers relocation nor migrates state, and the old registration remains until explicit cleanup. When that exact root cannot be found, Devbox classifies the retained registration as a Missing-root Project registration without inferring why; Cleanup inspection and previews display that status together with the original absolute path.

Missing-root Project registrations are removed only by the global `devbox cleanup --missing-projects` mode. It extends the normal Cleanup plan with every currently Missing-root registry entry, displaying each exact original root and assigned flat state directory in the same single confirmation as stopped Sandbox, temporary-file, and old-image cleanup; any running Devbox Sandbox blocks the whole combined operation before deletion. After removing planned stopped Sandbox and Compose resources, Devbox rechecks each candidate root and its resources, retains and reports any entry whose root has reappeared or whose resources still exist, and otherwise deletes its retained Compose, Local configuration, and empty state directory before atomically removing the selected registry entries last. It never touches an original Project path or any Docker volume, and `--dry-run` and `--yes` follow the normal Cleanup contract.

`devbox rm [--yes]` is a Project-local teardown and unregister operation for the current existing Project and never invokes Cleanup. It displays the exact Project root and the Sandbox, container writable layer, retained Compose, Local configuration, and registration selected for removal; an interactive terminal requires one confirmation, while a non-interactive caller must pass `--yes`, which bypasses only the prompt. After confirmation it applies `down` semantics, removes retained Project files and the empty mirror, then atomically removes the Project registry entry last; any earlier failure keeps the entry registered for a forward retry. It never changes Global configuration or the Platform lock and never removes Agent homes, Workspace images, or Docker volumes.

Neither `devbox rm` nor `devbox cleanup --missing-projects` modifies Global configuration. Removing the last Local selection of a Runtime only clears that Runtime's removal guard; it never implicitly removes the Runtime from the Configured Runtime set, prunes the Configured Agent set, or invokes `update` or `build`. Those user-scope desired-state changes remain a separate explicit `config -g` operation.
