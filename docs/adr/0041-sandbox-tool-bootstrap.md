# Bootstrap Node tools and AI Agents once per Sandbox

The common Workspace image contains the Base profile and Configured Runtime trees but no Devbox-added Node global tools or AI Agent installation. Every Agent catalog entry must provide an official Runtime-independent installation path compatible with the Base profile and runnable by the Sandbox user without elevation; an Agent whose installer requires root is ineligible. On the first start of every new or replacement Sandbox, entrypoint bootstrap installs the complete Configured Agent set through those paths; when the Project also has Selected Node, it separately uses that Node's native npm global prefix to install the complete Devbox-managed npm tool set.

Entrypoint treats only one container-local completion marker written atomically after every applicable Node-tool and configured Agent installer exits `0` as a completed bootstrap; executable existence is insufficient because an upstream installer may publish a launcher before finishing. Devbox streams installer output to Compose logs but performs no post-install command lookup, version check, or Agent smoke test. A Sandbox with no applicable Node tools and an empty Configured Agent set still writes the same zero-work marker so bootstrap has one completion rule. Any network, installer, or managed-tool failure leaves the marker absent and makes entrypoint exit nonzero, so the detached container stops while retaining partial writable-layer output and Compose logs for diagnosis. The next start of that same container reruns the complete idempotent sequence in its fixed order; Compose-driven recreation instead discards the partial layer and starts from the image. The marker is replacement-scoped state, not a version registry, user-editable interface, Sandbox readiness signal, or proof that the long-lived process is alive.

A successful bootstrap remains in the container writable layer. Stop and restart reuse it without network access or a latest check; container replacement discards it and installs then-current floating releases again. Different Project Sandboxes may therefore retain different tool and Agent versions. Changing the Configured Agent set takes effect for a Project through container replacement rather than `build`; a Project without Selected Node skips Node global-tool installation but still installs every Configured Agent and mounts every corresponding Agent home.

Configured Agent drift is applied through ordinary Compose convergence rather than a Devbox replacement prompt. `config -g` changes only Global configuration; the next Project `up` renders that set into retained Compose and directly runs `docker compose up -d`, which may recreate either a running or stopped container and discard its old completion marker and writable layer. A recreated Sandbox bootstraps the complete current Configured Agent set, while a container Compose leaves unchanged retains its earlier installed set. Removing an Agent never uninstalls it in place, and adding one never installs it into an unchanged container.

For Node's base global tools, bootstrap preserves npm's native prefix, global `node_modules`, executable, and per-user cache locations and runs `npm install -g npm@latest corepack@latest`, `corepack enable pnpm`, `corepack install -g pnpm@latest`, then `npm install -g -f yarn@1`. pnpm remains Corepack-owned, while Yarn Classic deliberately replaces Corepack's Yarn shims. Other Devbox-managed npm globals use the same native prefix and `npm install -g` installation model.

Node-tool bootstrap keeps the Selected Node tree root-owned. The entrypoint uses root only for npm global-prefix writes and `corepack enable pnpm`, invokes `corepack install -g pnpm@latest` as the host-matched Sandbox user so Corepack's default payload lives in that user's normal home cache, and runs every Runtime-independent Agent installer as the same Sandbox user regardless of the Toolchain. It never recursively changes ownership of the Node tree or makes the global prefix writable to later Project processes; this avoids per-container copy-up of the complete Runtime and prevents ordinary Sandbox code from replacing Node or managed global tools.

Runtime-independent Agent installers run as the host-matched Sandbox user and retain their official payload, launcher, and shell-profile changes. Devbox does not relocate their files, add `~/.local/bin` or another Agent launcher directory to the Compose container environment, or create command projections. Agent command discovery is supported only through `devbox sh`'s interactive login shell applying the upstream-written profile; even non-interactive `bash -lc` is not guaranteed because upstream installers may update an interactive-only profile. Direct `devbox exec <agent>`, Compose commands, entrypoint commands, Agent-to-Agent direct subprocess spawning, and other shell-free lookup are likewise unsupported. Shell profiles and Agent launcher locations are writable by the same Sandbox user as Project commands and Agents, so this lookup rule is a usability contract rather than an executable-integrity or prompt-injection defense.

This supersedes ADR-0032's Configured-Agent Workspace build input, ADR-0040's build-time floating Agent installation, and ADR-0039's build-time global-tool refresh. It restores per-Sandbox executable installation from ADR-0009, applies Configured Agents to every Sandbox independently of Selected Runtimes, installs Node tools only when Selected Node exists, and keeps shared Agent homes separate from executable payloads.
