# Run Sandboxes as a host-matched non-root user

The Base image contains one `devbox` account and group. Generated Compose passes the numeric UID and GID of the developer invoking Devbox as machine-derived Sandbox inputs rather than Project or Local configuration. A Sandbox entrypoint starts as root only long enough to validate those nonzero IDs, align the `devbox` account and group, and make Devbox-managed writable paths and mounted volumes accessible; it never recursively changes ownership of the Project workspace. Failure to align the IDs or write the mounted workspace prevents readiness with an actionable error rather than falling back to root.

After preflight, the entrypoint installs and runs the selected AI Agent as the Sandbox user and drops root before starting the long-lived Sandbox process. `devbox sh` and `devbox exec` likewise invoke Compose exec with that exact numeric UID and GID, so interactive shells, project commands, package managers, and AI Agents create host workspace files as the developer rather than root. Root is an implementation-only bootstrap identity and not the supported interactive user.

UID and GID affect generated Compose and whether an existing Sandbox must be replaced, but do not affect the Base image, Runtime bundles, or Workspace fingerprint. Devbox-owned writable paths include the container-local Corepack home and the selected Agent home; Project files remain governed by the bind mount and the matched numeric identity. This model applies on Linux, WSL2, and macOS Docker Desktop without reading or importing host account files.

The Base does not install or configure `sudo`, expose a root credential, or provide another supported elevation path. Sandbox processes therefore cannot mutate system packages through `apt`; a generally required native package belongs in the versioned Base recipe and reaches users through explicit Base update. Direct host-side Docker intervention remains outside the Devbox interface and support boundary.

## Sandbox user evidence

On 2026-08-02, a disposable integrated prototype ran Base-only, Node-only, PHP-only, and combined Workspaces on WSL2 `linux/amd64` as the host-matched numeric identity `1000:1000`. Every variant created Project files with that ownership and used the intended login-shell path; the combined Workspace retained cross-Runtime invocation. The Sandbox user could write only the intended Corepack state subtree while PHP extension paths, other Runtime paths, and Debian package state remained immutable, and no supported `sudo` path existed. Stop and restart preserved downloaded Corepack state, while container replacement removed it and retained the image-preloaded default. This evidence confirms the layout for the exercised WSL2 host and does not replace the separate Linux and macOS Docker Desktop verification branch.
