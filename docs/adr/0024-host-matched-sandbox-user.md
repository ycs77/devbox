# Run Sandboxes as a host-matched non-root user

ADR-0041 supersedes ADR-0032's image-owned Agent executables and restores first-start Sandbox bootstrap for Devbox-added Node global tools and Configured Agents. The host-matched Sandbox-user and writable-path rules remain in force.

The Base image contains one `devbox` account and group. Generated Compose passes the numeric UID and GID of the developer invoking Devbox as machine-derived Sandbox inputs rather than Project or Local configuration. A Sandbox entrypoint starts as root to validate those nonzero IDs, align the `devbox` account and group, make Devbox-managed writable paths and mounted volumes accessible, and perform only the root-required npm global-prefix writes when Selected Node tools require incomplete first-start bootstrap. It never recursively changes ownership of the Project workspace or any Selected Runtime tree. Failure to align the IDs, write the mounted workspace, or complete bootstrap makes entrypoint exit nonzero and stops the detached container rather than falling back to a root Sandbox.

For an incomplete bootstrap, the entrypoint performs npm global-prefix installation and Corepack shim creation as root only when the Project has Selected Node, then invokes Corepack's per-user payload setup when applicable and every Configured Agent's Runtime-independent installer as the host-matched Sandbox user. It writes the completion marker only after all applicable steps succeed, then drops root before starting the long-lived Sandbox process. `devbox sh` and `devbox exec` likewise invoke Compose exec with that exact numeric UID and GID, so interactive shells, project commands, package managers, and AI Agents create host workspace files as the developer rather than root. Root is an implementation-only preflight and Node-tool bootstrap identity and not the supported interactive user.

UID and GID affect generated Compose, Agent-home access, per-user package-manager and installer state, and whether an existing Sandbox must be replaced, but do not affect the Workspace image or Runtime bundle contents. Devbox-owned writable paths include the container-local package-manager caches and mounted Agent homes; the Selected Node prefix remains root-owned outside the entrypoint's managed bootstrap writes, while Project files remain governed by the bind mount and matched numeric identity. The current contract applies to the supported WSL2 `linux/amd64` host without reading or importing host account files.

The Base does not install or configure `sudo`, expose a root credential, or provide another supported elevation path. Sandbox processes therefore cannot mutate system packages through `apt`; a generally required native package belongs in the `ubuntu:24.04` Base plan and reaches new or recreated Sandboxes only after explicit `update`, `build`, and `up` stages. Direct host-side Docker intervention remains outside the Devbox interface and support boundary.

## Sandbox user evidence

On 2026-08-02, a disposable integrated prototype ran Base-only, Node-only, PHP-only, and combined Workspaces on WSL2 `linux/amd64` as the host-matched numeric identity `1000:1000`. Every variant created Project files with that ownership and used the intended login-shell path; the combined Workspace retained cross-Runtime invocation. The Sandbox user could write only the intended Corepack state subtree while PHP extension paths, other Runtime paths, and Debian package state remained immutable, and no supported `sudo` path existed. Stop and restart preserved downloaded Corepack state, while container replacement removed it and retained the image-preloaded default. This evidence confirms the layout for the exercised WSL2 host and does not replace the separate Linux and macOS Docker Desktop verification branch.

On 2026-08-03, a focused Claude Code bootstrap prototype exercised the same WSL2 `linux/amd64` identity through installation, ordinary Agent configuration, stop and restart, and container recreation. Root performed only numeric identity and writable-path preflight; the official installer and subsequent Agent commands ran as `1000:1000`. The Agent home, launcher, installed version payload, cache entries, bootstrap-created files, and Project probe files were all owned by that matched identity, with no recursive Project ownership repair or unexpected root-owned artifact. This extends the prior evidence to the selected Agent bootstrap path without widening the platform claim.
