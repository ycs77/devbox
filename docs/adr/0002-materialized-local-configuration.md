# Materialize complete project configuration in user scope

The first `devbox init` for a Project runs only in an interactive terminal and materializes one complete Local configuration in user scope; the initial release provides no non-interactive initialization mode. Project configuration values are fixed and displayed without prompting, while the user answers every option the project leaves open. For an open Toolchain choice, Devbox detects supported project manifests such as `composer.json` and `package.json`, presents the inferred Runtimes and release lines as editable suggestions, and falls back to Built-in defaults when detection is inconclusive; detection never fixes a Project option automatically. Repeating `init` reports that the Project is already initialized and changes nothing, while later configuration changes use a separate operation. Before each start, current project-fixed values are synchronized into the Local configuration, and execution reads only the resulting complete configuration; removing a project-fixed value preserves its last local value but makes it user-editable. This gives projects shareable control over selected choices without requiring every personal choice to live in the repository.

Later interactive changes use `devbox config`. It validates the current Project and Local configuration, applies current Project-fixed values in memory before presenting the form, displays those fixed values without allowing edits, and prompts for every open option using the current Local values. A value whose Project constraint was removed retains its last Local value and becomes editable immediately. After the questions, the command displays only actual changes and asks for one confirmation that defaults to Yes; no changes require no confirmation or file rewrite, while cancellation or No writes nothing. A confirmed change atomically rewrites `config.yaml` in the canonical format. `config` is unavailable outside an interactive terminal, where users instead edit the supported YAML interface directly. It never invokes Sync, changes the Platform lock, prepares a Workspace image, renders Compose, operates Sandbox lifecycle, or performs any Docker work; its changes reach derived state through the next `sync` or `up`.

`init` does not invoke Sync, create or modify the Platform lock, prepare Workspace images, render generated Compose, create or start a Sandbox, or perform any Docker operation.

Local configuration is also a supported human-editable YAML interface with its own required integer `version: 1`, independent of the Project configuration schema version. Devbox validates it whenever an operation requires current Local configuration and refuses unsupported versions, unknown keys, or invalid and incomplete content rather than repairing or ignoring them silently; CLI writes are atomic and use one canonical YAML format, preserving values but not comments, key ordering, or original formatting.

For every supported older Local-configuration schema, ordinary Project operations that require current Local configuration migrate `config.yaml` automatically under the Project lock. Devbox applies a complete deterministic, lossless, forward-only chain one schema version at a time, adapts the result to the current domain model, and validates it before writing. Sync combines that migration with any current Project-fixed synchronization into one canonical atomic rewrite rather than publishing intermediate schema versions. Comments, key ordering, and original formatting receive no preservation guarantee because the file already has one canonical CLI serialization.

If any migration step requires a user choice or would discard user intent, a non-interactive operation fails without guessing or rewriting and directs the user to the existing interactive `devbox config` flow. `config` loads the supported older values into the current form, applies current Project-fixed values, and writes the current schema only after the existing final confirmation; cancellation or No leaves the older file unchanged. Devbox adds no separate `migrate` command.

Devbox exposes a non-starting `devbox sync` operation that validates the current Project and Local configuration and synchronizes current project-fixed values into the Local configuration before preparing derived state. `devbox up` invokes the same Sync module automatically, so an explicit sync is optional rather than a prerequisite; operations that do not apply a new Sandbox definition use the most recently synchronized generated Compose state.

The Sync module's sole external operation is `synchronize({ project, lease, signal })`, where `project` is an already registered Project identity, `lease` is the opaque `ProjectLockLease` capability for that same Project, and `signal` carries operation cancellation. Sync rejects a mismatched or released lease. It owns loading and validating Project and Local configuration, materializing any current Project-fixed values, forming the Resolved configuration, preparing and activating any required Platform candidate through Build, and atomically publishing the retained Compose definition last. CLI operations resolve the current registered Project and present Sync's result but do not assemble those stages themselves.

On success, `synchronize({ project, lease, signal })` returns one `SynchronizedProject` containing the retained Compose location, desired stable Workspace tag, and a summary of whether this call changed Local configuration, the Platform lock, or Compose. The explicit `sync` command uses that result for human-readable output, while `up` uses the same result to continue Sandbox lifecycle without rereading files or reconstructing Sync's internal stages. Candidate locks, temporary files, and Build pipeline details never appear in this result.

Sync commits derived state in safe dependency order rather than emulating a cross-file transaction. A valid project-fixed synchronization is atomically written to `config.yaml` even if later artifact preparation fails, because it is the current Local configuration rather than a candidate artifact; subsequent Platform and Compose steps may then be retried without rolling that configuration back.
