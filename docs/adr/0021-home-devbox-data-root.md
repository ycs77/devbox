# Store host-side Devbox data under ~/.devbox

Devbox stores all of its host-side user-scope files under `~/.devbox` on Linux, WSL2, and macOS rather than using XDG or macOS-specific application directories. Per-Project Local configuration and generated Compose state share mirrored Project directories, the active Platform lock is the machine-owned YAML file `~/.devbox/platform-lock.yaml`, and Docker-managed volumes remain in Docker storage. Project data mirrors the absolute Project root beneath `~/.devbox/projects/`: path separators form nested directories, while each path segment is reversibly escaped when needed for safe storage rather than replaced by an opaque hash. Each mirrored Project directory stores its supported human-editable Local configuration as `config.yaml` and its machine-owned generated Compose definition as `compose.yaml`; the presence of `config.yaml` alone registers the Project even when its contents are invalid, and Devbox discovers and reports such Projects by scanning those files instead of maintaining a separate central registry or index.

Within this root, each Project's `config.yaml` is the only Devbox-supported human-editable file interface. The Platform lock, temporary candidate files, generated Compose definitions, and any other Devbox state files are machine-owned: users may inspect readable contents for troubleshooting, but manual edits are unsupported and neither their serialization nor internal paths are external compatibility contracts. Agent homes retain their separately defined ownership and write behavior rather than becoming Devbox configuration files.

The initial release creates no host-side log or cache directory. Commands report directly through their terminal output, while Docker and BuildKit retain their own rebuildable cache. After its Sandbox preflight and teardown, `devbox cleanup` removes disposable machine-owned temporary files and eligible Devbox-owned image tags, including unreferenced `devbox-workspace:<fingerprint>` tags and `devbox-base:<image-id-hex>` tags not protected by the active Platform lock. It never invokes Sync or changes Project registrations, retained Local configuration and Compose state, the active Platform lock, or any Docker volume. It also does not prune BuildKit cache because the existing builder boundary cannot reliably attribute that cache to Devbox alone; Docker or the user retains control of it rather than Devbox introducing a dedicated builder only for cleanup.
