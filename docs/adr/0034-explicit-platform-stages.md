# Separate configuration, locking, building, and Sandbox lifecycle

> **Current status (2026-08-14):** ADR-0048 supersedes this ADR's Platform-lock and explicit `update` contract. The current direction uses Global `build.node` configuration plus packaged Runtime recipes, does not create `platform-lock.yaml`, and defers Project-specific Runtime selection and Local configuration. General separation of configuration, Build, and Sandbox lifecycle remains only where it does not conflict with ADR-0048.

Devbox adopts an explicit staged workflow instead of self-applying configuration. Interactive `init` registers the current Project and initializes its Local configuration and, only when absent, Global configuration without resolving artifacts or invoking Docker; `config` edits only Local configuration, while `config -g` edits only Global configuration. `update` is the only command allowed to modify an existing Platform lock and may also create one by resolving the current Base inputs and Configured Runtime source coordinates and trusted release-key policy without invoking Docker.

Devbox exposes a public `build` command that changes neither configuration nor an existing Platform lock. If the Platform lock is absent, `build` may bootstrap it by resolving and atomically creating the complete source-coordinate plan before building; if it exists, `build` skips resolution and consumes it without refreshing or rewriting any entry. Build then downloads and verifies the locked Runtime sources according to the lock-snapshotted trust policy, regenerates the machine-owned Workspace context, and invokes Docker directly against `devbox-workspace:latest`. `up`, `stop`, and `down` perform only their Compose lifecycle operations.

When a Platform lock exists, `build` requires its Runtime family and release-line keys to match the current Configured Runtime set exactly. A missing or extra entry fails before Docker work and directs the user to `devbox update`; Build never ignores current desired state, supplements the lock in memory, or emits an image containing exact artifacts absent from the lock.

`up` invokes detached Compose against the last successfully published `devbox-workspace:latest` and neither invokes Build nor verifies that the mutable tag was produced from the current Platform lock. Users explicitly advance configuration, source resolution and trust policy, image materialization, and Sandbox lifecycle through `config` or `config -g`, `update`, `build`, and `up`. Skipping `build` may therefore start an older image; if it lacks a Selected Runtime, entrypoint later exits nonzero while the already detached `up` may have returned success.

`config` may select only Runtime entries already present in the Configured Runtime set. A missing entry fails before saving and directs the user to add it through `config -g`; Project configuration never expands Global configuration implicitly.

`up` is the only command that regenerates the current Project's machine-owned retained Compose definition. It reads current Local and host inputs, atomically replaces `compose.yaml`, and then invokes Compose; fixed image reference `devbox-workspace:latest` means `build` never updates retained Project definitions. `stop` and `down` use the last retained definition without regeneration so they continue targeting the resources that were actually published.

Build failure creates no durable dirty, failed, or freshness marker. A pre-existing or bootstrap-created Platform lock remains, the prior `devbox-workspace:latest` remains unchanged, and the generated build context is disposable input overwritten by the next invocation. The failed command's nonzero exit and diagnostics are the only failure record; retry is another explicit `build`, and `up` remains free to start the last successful image.

A successful `docker build` exit is the complete Workspace build success contract, and a successful `docker compose up -d` exit is the complete `up` contract. Devbox performs no post-build or post-start Runtime, package-manager, Agent, final-image, Docker-health, or Project smoke verification and keeps no verification result. Entrypoint independently checks only Selected Runtime path structure and the exit status of applicable bootstrap installers. Actual tool execution, version suitability, native dependency loading, and Project behavior belong to Project commands and tests.

The explicit stages are independently forward-only. `update` atomically replaces the complete Platform lock after successful resolution; a later Build failure never restores its prior bytes. A successful Docker build leaves the new `latest` in place even if a later `up` fails. `up` atomically retains its newly rendered Compose definition before invoking Compose and does not restore the prior definition when Compose fails. Devbox keeps no cross-stage backups or transaction metadata; recovery reruns only the failed stage.

`init`, `config`, `config -g`, `update`, and `build` never invoke Compose or create, start, stop, remove, or replace a Sandbox container. Moving `latest` during `build` does not affect existing containers. Only explicit `up`, `stop`, and `down` perform their named Sandbox lifecycle effects.

This supersedes ADR-0030's self-applying `config` and `config -g` reconciliation and ADR-0016's prohibition on a public build command. Configuration, source resolution and trust-policy snapshotting, image materialization, and Sandbox lifecycle may now be intentionally out of sync between explicit commands; ADR-0047 defines the Runtime verification boundary inside Build.
