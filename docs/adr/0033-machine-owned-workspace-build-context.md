# Keep one machine-owned Workspace build context

Devbox keeps the single generated common Workspace build context directly at `~/.devbox/build/`, with its Dockerfile, defensive `.dockerignore`, and only the packaged recipe assets required by the current build set. The explicit `build` command regenerates the complete machine-owned contents from Global `build.node` configuration and the packaged Runtime recipes, orders variable entries canonically, and invokes one `docker build` operation with that directory as its context. The current prototype keeps the Base and configured Runtime stages in this one context, so it does not add a `workspace/` child directory. The fixed path is not a success marker, cache identity, user-editable interface, or persisted candidate: each Build invocation may replace it before Docker work, and failure leaves no durable Build state.

Devbox never uses `~/.devbox` itself as a Docker build context because it contains the Project registry, Global configuration, future Project state, and retained Compose state that must not be sent to Docker. Build must serialize access to its shared context, but no Platform-lock coordination or lock-file read is part of the current recipe-driven decision. A later invocation overwrites incomplete or stale generated contents rather than trusting them as prepared state.
