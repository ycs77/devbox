# Keep one machine-owned Workspace build context

Devbox keeps the single generated common Workspace build context directly at `~/.devbox/build/`, with its Dockerfile, defensive `.dockerignore`, and only the packaged recipe assets required by the current build plan. The explicit `build` command regenerates the complete machine-owned contents from the fully resolved Base and Configured Runtime set, orders variable entries canonically, and invokes one `docker build` operation with that directory as its context. ADR-0041 removes the Configured Agent set from this context because every Sandbox installs Agents during first-start bootstrap independently of its Toolchain. The current design keeps the Base and Configured Runtime stages in this one context, so it does not add a `workspace/` child directory. The fixed path is not a success marker, cache identity, user-editable interface, or persisted candidate: each Build invocation may replace it before Docker work, failure leaves no dirty state, and Cleanup may remove it only under the shared-artifact coordination rule that will be decided with Build and Update.

Devbox never uses `~/.devbox` itself as a Docker build context because it contains the Project registry, Global configuration, Platform lock, and per-Project Local and retained Compose state that must not be sent to Docker. Build must serialize access to its shared context, but ADR-0045 intentionally defers how `build` and other shared Docker or Platform operations coordinate with Project command locks; no former user-scope lifecycle-lock rule remains current for those future operations. A later invocation overwrites incomplete or stale generated contents rather than trusting them as prepared state.
