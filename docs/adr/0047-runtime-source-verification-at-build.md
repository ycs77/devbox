# Verify Runtime source integrity during Build

Platform lock version 1 stores the Build coordinates and trusted release-key policy needed to assemble each Runtime, not the Node archive bytes or a checksum observed during `update`. Each packaged Node release-line recipe owns its hard-coded trusted release-key fingerprint list; `update` selects the exact revision, records the archive and signed-checksum manifest URLs, and snapshots that fingerprint list without downloading or authenticating the Runtime archive. `build` obtains the listed public keys through the recipe's keyserver policy, verifies the signed checksum manifest, derives and verifies the selected archive checksum, and extracts the Runtime in the same inline Dockerfile; it accepts any signer represented by a fingerprint in the lock. The Ubuntu Base remains digest-pinned and permanently includes the tools required by this one-stage verification flow. Its curated package names are resolved from Ubuntu's live archive after the Base installs `ca-certificates` and switches the archive URLs to HTTPS; package revision drift between Builds is accepted and is not represented by an apt snapshot field.

This moves Runtime source verification from the host-side `update` command into Docker Build, avoids embedding release-key material in the CLI or duplicating archive checksums in the Platform lock, and deliberately accepts that a later Build may receive different bytes for the same exact Node revision if the official signed manifest, archive source, or live Base package repository has changed.
