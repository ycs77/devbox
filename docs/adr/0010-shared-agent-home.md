# Share one Devbox-managed Agent home across projects

Devbox keeps one writable user-scope Agent home per AI Agent and mounts it into every Sandbox that selects that Agent, while never mounting or importing the developer's normal host Agent home. The initial release exposes no Project-independent `devbox auth`, logout, or Agent-reset operation. A user authenticates by running the installed Agent inside any Project Sandbox that selects it and completing the Agent's upstream flow; the resulting credentials, settings, history, trust state, hooks, MCP configuration, and other mutable Agent state use the upstream-compatible Agent home and are then shared across Projects. This deliberately accepts cross-Project visibility and modification for a simpler lifecycle and avoids splitting credentials from state through mount or symlink behavior that the prototype found incomplete or incorrect. The Agent executable itself is installed into each Sandbox's writable container layer rather than this shared home, so recreating one Sandbox cannot replace the executable used by another. A future focused design may add Project-independent authentication without making it a first-release placeholder.

Agent home Docker volumes are user-data resources rather than rebuildable cache. `cleanup`, `down`, and `rm` never delete them, and Devbox exposes no generic volume-deletion option. A future Agent-specific reset lifecycle may deliberately remove one named Agent home, but its command and confirmation contract are outside the initial Cleanup design.

## Agent home boundary evidence

On 2026-08-03, the WSL2 `linux/amd64` Claude Code prototype mounted one Docker volume at `/home/devbox/.claude` and set `CLAUDE_CONFIG_DIR` to that same Agent home. An actual unauthenticated `claude mcp add --scope user` operation wrote its user configuration and backups inside that directory rather than at `~/.claude.json`; the configuration remained usable after container recreation. A non-secret persistence sentinel followed the same lifecycle. In contrast, the Agent launcher and version payload under `~/.local` and rebuildable runtime caches under `~/.cache` belonged to the container layer and were recreated or discarded with the container.

The prototype passed no credential environment variables, mounted no host Agent home, reported Claude Code as unauthenticated, and observed no credential file. Claude Code's documented Linux credential location under `CLAUDE_CONFIG_DIR` therefore falls inside the mounted Agent home without importing or exposing a real credential during the experiment. This establishes the storage and authentication boundary, but deliberately does not claim that a live upstream login, token refresh, or logout flow was exercised.
