# Feasibility of Pure-JavaScript Cross-Process Locking

Research date: 2026-08-03. Scope is Devbox v1 WSL2 `linux/amd64`, Node `>=22`, examining only locking across independent CLI processes; does not revisit existing ADRs and does not extend to other host primitives.

> **Current decision override:** ADR-0045 supersedes the former recommendation to retain `devbox-host`. Devbox's current pre-release contract intentionally accepts simple non-waiting filesystem command markers for configuration and Project operations, with manual cleanup after abnormal termination. ADR-0046 records the related packaging consequence: one pnpm-managed package at the repository root, with no workspace graph, platform package, native Go module, or multi-package release flow. The source facts and candidate comparisons below remain useful historical evidence, but ADR-0045 and ADR-0046 are the current product decisions.

This document marks content directly supported by official documentation or first-party sources as **"Source fact"**, and marks judgment applied to the Devbox contract as **"Devbox analysis"**. Such "pure JS" must also be differentiated: whether the JavaScript code additionally carries a native artifact and whether the underlying implementation is genuinely done in JavaScript are two different things.

## Current decision

ADR-0045 removes the planned Go helper from the current configuration and Project-operation scope. Devbox uses one Global command marker and one Project command marker per Project under `~/.devbox/locks/`; lock acquisition is non-waiting, a busy scope fails immediately, and normal command completion removes the marker. Forced termination may leave a marker for manual cleanup after the user confirms that no Devbox process is running.

`up` uses only its Project marker, reads a configuration snapshot, and holds the marker through the complete `docker compose up -d` command. Different Projects can run `up` concurrently; a later command for the same Project fails until Compose returns. `config -g` uses only the Global marker and may run during `up`; Project `config`, `init`, `rm`, and Missing-root cleanup use the Global marker plus relevant Project markers. Future `build` and `update` coordination remains undecided.
ADR-0046 records the related packaging consequence: the CLI is one pnpm-managed package at the repository root, with one package lockfile and one npm release boundary. The helper-specific packaging and release analysis below is historical and does not prescribe a current implementation.

The remainder of this document records the source facts and alternatives considered under the previous helper-backed contract. Those comparisons explain the accepted reliability trade-off; they no longer prescribe the current implementation.

## Previous Devbox Lock Contract

This research is based on the former observable contract of earlier decisions:

- A Project-local lifecycle first acquires a user-scope lifecycle **shared** lock, then acquires that Project **exclusive** lock; different Projects can therefore proceed in parallel, while the same Project is serialized.
- Global `update`/Base update/`cleanup` acquires a user-scope lifecycle **exclusive** lock, excluding all Project operations.
- Platform mutation and each Workspace fingerprint are separate exclusive resources; different fingerprints can proceed in parallel.
- The fixed rank is `lifecycle → Project → Platform mutation → fingerprint`, released in reverse order. This is deadlock prevention and does not require atomically acquiring the full set of locks in a single syscall.
- When unavailable, wait without a fixed timeout and display the waiting resource; pending waits can be cancelled via the operation `AbortSignal`, and cancellation does not alter protected state.
- After holder normal release, parent EOF, process crash, or `SIGKILL`, ownership must be released by the OS; it must not wait for manual deletion of stale files, nor allow another still-living process to mistakenly take over.
- Lock target files carry no generation or domain state; there is no daemon, socket, or persistent lease registry.

Currently, one exact-version `devbox-host` child per lock scope holds a kernel advisory-lock FD; stdin EOF or helper exit releases it. Linux `flock(2)` itself provides `LOCK_SH`, `LOCK_EX`, blocking/`LOCK_NB`; the lock is bound to the open file description and is released when all associated FDs are closed; Linux `fcntl` record locks are also automatically released upon process termination. [Project lifecycle lock decision](../adr/0001-generated-compose.md), [Project resource rank decision](../adr/0007-global-platform-lock.md), [Linux `flock(2)`](https://man7.org/linux/man-pages/man2/flock.2.html), [Linux `fcntl` locking](https://man7.org/linux/man-pages/man2/fcntl_locking.2.html)

### "Fairness" and "Atomic Multi-Lock" Are Not Implicit Guarantees

**Source fact:** Linux `flock(2)` documentation describes blocking, shared/exclusive, and release; it does not promise waiter FIFO; nor does it perform deadlock detection. `fcntl(F_SETLKW)` has limited deadlock detection for traditional process-associated record locks, but still has no syscall that atomically acquires locks on multiple pathnames. [`flock(2)`](https://man7.org/linux/man-pages/man2/flock.2.html), [`fcntl` locking](https://man7.org/linux/man-pages/man2/fcntl_locking.2.html)

**Devbox analysis:** Therefore "fair" in this matrix splits into two layers: avoiding known reader/writer starvation, and strict FIFO. The existing contract requires waitability, cancellability, and a fixed rank, and does not derive a strict FIFO guarantee from the kernel API. Any candidate claiming to be "fairer than the status quo" must maintain its own queue. The correct replacement for multiple locks is to continue using a fixed rank, hold already-acquired prefixes while waiting, and release in reverse on cancellation; demanding all-or-none atomic vector acquisition is a new requirement, not a capability of the current helper.

## Candidate 1: Node Built-in `fs`, Open Flags, and `mkdir`

### Node 22 Through Current Has No Built-in Advisory Lock

**Source fact:** Node v22.23.2 `fs` API's `FileHandle`, callback, and sync method listings have no `flock`/`fcntl`; the current v26.5.1 `fs` API also has none. Node's underlying libuv `uv_fs_type` and FS API listing includes open, close, read, write, mkdir, rename, unlink, fsync, etc., with no lock operation; the current Node native FS binding source likewise exposes no `flock`/`fcntl` wrapper. [Node v22.23.2 `fs`](https://nodejs.org/docs/latest-v22.x/api/fs.html), [Node v26.5.1 `fs`](https://nodejs.org/docs/latest/api/fs.html), [libuv FS operations](https://docs.libuv.org/en/v1.x/fs.html), [Node v26.5.1 `src/node_file.cc`](https://github.com/nodejs/node/blob/v26.5.1/src/node_file.cc)

This does not mean Linux lacks primitives; Linux has both whole-file `flock`, POSIX process-associated record locks, and Linux-specific OFD record locks. The difference is simply that Node built-in does not expose them. Traditional `fcntl` locks also have the semantics that "when a process closes any FD for the same file, all record locks held by that process on that file are released"; `flock`/OFD locks are instead bound to the open file description, more closely matching the current per-scope single-FD ownership model. [Release differences in Linux `fcntl` locking](https://man7.org/linux/man-pages/man2/fcntl_locking.2.html)

### What `open('wx')` Actually Guarantees

**Source fact:** Node's `'wx'` is like `'w'` but fails if the pathname already exists; `'x'` corresponds to `O_EXCL`, which, when combined with `O_CREAT`, reports an error if the path exists (including dangling symlinks). Node also explicitly notes that the exclusive flag may not work on network filesystems. Linux `open(2)`'s guarantee is that `O_CREAT | O_EXCL` combines "check existence" and "create" into an atomic operation; it is not placing an advisory lock on an existing file. [Node file-system flags](https://nodejs.org/docs/latest-v22.x/api/fs.html#file-system-flags), [Linux `open(2)` `O_EXCL`](https://man7.org/linux/man-pages/man2/open.2.html)

On a single local filesystem on WSL2 Linux home, when all cooperating processes use the same path and `'wx'`, only one creator wins per race; but ownership means "the directory entry still exists", not "the creator FD is still alive". A successful creator closing its FD or being `SIGKILL`-ed does not unlink; another process can still open that pathname with ordinary `'r'`/`'w'`. It is natively only an exclusive create marker: no shared mode, blocking wait, owner queue, global-reader barrier, or crash release.

`mkdir(lockPath)` has a similar mutual-exclusion basis: an existing directory causes a same-name `mkdir(2)` to return `EEXIST`. The mature `proper-lockfile` first-party source uses exactly `mkdir` acquisition, directory `mtime` heartbeat, stale threshold, retry, and exit-time `rmdir` to compose an exclusive lock; the source also explicitly lists that `SIGKILL` or VM fatal crash cannot execute graceful cleanup. [Linux `mkdir(2)`](https://man7.org/linux/man-pages/man2/mkdir.2.html), [`proper-lockfile` v4.1.2 acquisition/heartbeat source](https://github.com/moxystudio/node-proper-lockfile/blob/v4.1.2/lib/lockfile.js), [`proper-lockfile` graceful-exit limitation](https://github.com/moxystudio/node-proper-lockfile/blob/v4.1.2/README.md#graceful-exit)

### Specific Failure Modes of Heartbeat/PID Stale Detection

Linux `SIGKILL` and `SIGSTOP` cannot be caught, blocked, or ignored; therefore no `exit` handler can turn them into reliable cleanup. [Linux `signal(7)`](https://man7.org/linux/man-pages/man7/signal.7.html)

1. **SIGKILL: choose between safety and availability.** A creates a marker and is then `kill -9`'d. If B never deletes the marker, mutual exclusion is safe but the resource is permanently unavailable; if B treats it as stale after 10 seconds, crash recovery is delayed by at least 10 seconds, and the following "live-process misjudgment" breaks safety. `proper-lockfile`'s default stale/heartbeat is precisely the latter, and it uses `Date.now()` compared against directory `mtime`. [`proper-lockfile` stale check source](https://github.com/moxystudio/node-proper-lockfile/blob/v4.1.2/lib/lockfile.js)
2. **SIGSTOP, system suspend, event-loop stall: live owner gets stolen.** A holds the lock, then is `SIGSTOP`-ped, WSL/host suspended beyond the stale threshold, or the JS event loop cannot update mtime due to synchronous work/CPU starvation. B deletes the stale directory, creates a new lock, and enters the critical section; when A resumes, it continues from where it was stopped. Even if the next heartbeat `stat` finds the mtime is not its own and calls `onCompromised`, the overlapping window has already begun and cannot undo Docker commands or file publications that A has already sent. `proper-lockfile` source only checks mtime after the timer resumes execution, and its README acknowledges that "the marker being removed and immediately acquired by someone else" cannot be detected. [`proper-lockfile` compromised cases](https://github.com/moxystudio/node-proper-lockfile/blob/v4.1.2/README.md#compromised)
3. **Wall-clock jump: mtime lease is not a monotonic lease.** Both `Date.now()` and filesystem mtime are in the wall-clock domain. Linux `CLOCK_REALTIME` can undergo discontinuous jumps due to manual time setting and NTP; a clock jump forward can instantly judge a live heartbeat as stale, and a jump backward can keep a dead marker untakeable for longer than the configured threshold. [Linux clock semantics](https://man7.org/linux/man-pages/man3/clock_gettime.3.html), [`proper-lockfile` `Date.now()` comparison](https://github.com/moxystudio/node-proper-lockfile/blob/v4.1.2/lib/lockfile.js)
4. **PID reuse: `kill(pid, 0)` only answers whether this number exists right now.** Linux `kill(..., 0)` only performs a PID existence/permission check; `/proc/sys/kernel/pid_max` explicitly states that PIDs wrap around. A crashes leaving a PID; later, an unrelated process C gets the same PID; B will treat the dead lock as live. Adding `/proc/<pid>/stat` start time can reduce misidentification, but still requires atomically binding the marker token to that process instance; the PID itself is not an ownership capability. [Linux `kill(2)` signal 0](https://man7.org/linux/man-pages/man2/kill.2.html), [Linux `pid_max` wraparound](https://man7.org/linux/man-pages/man5/proc_sys_kernel.5.html)
5. **Stale-check/remove/recreate race.** B `stat`s the old marker as stale; before B `rmdir`s, A or another recovery process has already replaced the marker. Without an unforgeable token/inode revalidation in the protocol, B may delete the new owner's marker. Even using rename-to-quarantine and tokens to make a single exclusive marker safer still does not solve the live-but-paused holder being taken over by timeout.
6. **Reader/writer check-then-register race.** A pure marker has no shared mode. If each reader creates its own entry, reader R first checks "no writer", writer W then creates a writer marker, R then registers as a reader; both will enter simultaneously. Adding a turnstile/writer-pending marker and metadata mutex then requires stale recovery for that mutex itself; reader crashes also leave entries. Writer preference, FIFO, cancellation, and cleanup thus become a full lease coordinator rather than a handful of `fs` calls.
7. **Multiple locks are not a filesystem transaction.** A acquires rank 1 and already holds partial ownership while waiting for rank 2. A fixed rank prevents circular deadlock, and cancellation can clean up acquired markers in reverse; but there is no atomic all-or-none acquisition across pathnames. If each failure releases everything and retries, contenders can repeatedly collide synchronously causing livelock, with no fair ordering.

**Devbox analysis:** A JS retry timer can do `AbortSignal` cancellation and can create different markers based on resource hash to allow different Projects to proceed in parallel; what genuinely does not meet the contract is immediate and misjudgment-free release after crash, and building correct shared/exclusive barriers on top of that. Mature exclusive lockfile packages also do not provide the reader/writer, ranked multi-resource lease that Devbox needs. Therefore `open('wx')`, `mkdir`, lockfile+heartbeat cannot serve as a reliable replacement for the current helper.

## Candidate 2: `worker_threads.locks` / Web Locks

**Source fact:** Node added `worker_threads.locks` in v24.5.0. The official text precisely limits it to coordinating "multiple threads within the same process"; `locks.request()` supports `shared`/`exclusive`, pending request `AbortSignal`, `ifAvailable`, and `steal`, and the snapshot only describes held/pending locks of the current process. [Node v26.5.1 `worker_threads.locks`](https://nodejs.org/docs/latest/api/worker_threads.html#worker_threadslocks), [Node source documentation: same process](https://github.com/nodejs/node/blob/v26.5.1/doc/api/worker_threads.md#worker_threadslocks)

**Devbox analysis:** Within a single CLI process between main thread/Workers it possesses a very suitable named reader/writer API, but two independent `node` executables each have their own `LockManager` and same-named locks are invisible to each other. The Node 22 runtime also lacks this API entirely, unless the minimum is raised to v24.5.0. Routing all CLIs to a single resident Node process would enable cross-command coordination, but that is adding a daemon/coordinator and changing the independent CLI process contract. Conclusion: directly does not meet the goal and cannot serve as a fallback.

## Candidate 3: Unix Socket / TCP Bind

### Using Bind as an Exclusive Marker

**Source fact:** `net.Server.listen(path)` creates a Unix domain socket on Unix; the common error when the same port/path already has a listener is `EADDRINUSE`. A pathname socket remains on the filesystem after process crash, and Node officially notes it persists until unlinked; a Linux abstract Unix socket (Node path beginning with `\0`) automatically disappears after all open references are closed, and is a Linux-specific extension. Node supports abstract paths since v20.4.0. [Node IPC path and crash cleanup](https://nodejs.org/docs/latest/api/net.html#ipc-support), [Node `EADDRINUSE`](https://nodejs.org/docs/latest/api/net.html#serverlisten), [Linux `unix(7)` abstract/pathname semantics](https://man7.org/linux/man-pages/man7/unix.7.html)

For v1 WSL2, holding an abstract Unix listener can serve as a crash-safe exclusive name: another process binding the same name fails; after the holder is `SIGKILL`-ed the kernel closes the last reference and the name automatically disappears. Pathname Unix sockets reproduce the stale-file problem. TCP localhost ports under normal configuration can also provide one-listener exclusivity, but Node sets `SO_REUSEADDR` on all TCP sockets and additionally has the `reusePort` option allowing multiple sockets on the same port; ports are a limited numeric namespace, and resource→port collision, address family/interface, and occupation by other programs must also be defined—not as suitable as abstract Unix names. [Node TCP `SO_REUSEADDR`/`reusePort`](https://nodejs.org/docs/latest/api/net.html#serverlistenoptions-callback)

**Deficiencies:** The bind primitive only provides "this address has one owner"; it has no multiple shared holders, writer-pending gate, or atomic semantics for a user-scope global exclusive against all Project readers. EADDRINUSE is an immediate failure; waiting, backoff, fairness, and cancellation must all be written separately in JS. Hashing each Project/fingerprint into an independent abstract name allows parallelism but cannot let a global lifecycle owner exclude all existing or soon-to-appear Project addresses with a single bind. It also explicitly introduces live sockets; even without a separate daemon process, it still violates the current "no socket" boundary.

### Using Sockets as a Coordinator Transport

A Unix/TCP server can maintain in memory shared/exclusive holders for arbitrary resources, writer-preference/FIFO queues, fixed-rank checks, and per-request cancellation. Client connection EOF can notify the coordinator to release that client's leases. This is a candidate that can express the full contract in software, but it is not semantics that bind provides for free.

The specific failure scenario is coordinator C crashing: all client connections drop simultaneously, and C's in-memory lock table disappears. If clients still in the critical section continue working while a new C' accepts new locks, that is split brain; if all clients are required to cancel and stop protected work upon seeing EOF, it must also be proven that Docker children, publications, and cleanup all stop before re-acquisition, and the ambiguous outcome when C crashes right before or after a grant reply must be handled. For C to continue serving other commands after the original CLI exits, it is effectively a daemon; leader election and restart then require yet another cross-process primitive.

**Devbox analysis:** A coordinator can technically implement fairness and cancellation, but directly violates "independent CLI, no new daemon/socket". Using only abstract bind does not violate the persistent-state constraint and has excellent crash-release, but is still insufficient due to lack of reader/writer/global barrier.

## Candidate 4: Node Built-in SQLite Transaction

### Obtainable OS/Transaction Behavior

**Source fact:** `node:sqlite` was added in v22.5.0, no longer requires a flag as of v22.13.0 but is still experimental; as of v26.5.1 it remains a release candidate. It only exposes `DatabaseSync`; all APIs execute synchronously. `timeout` is the SQLite busy timeout: wait for the database lock for at most the specified milliseconds before returning an error; default 0. [Node v22 `node:sqlite`](https://nodejs.org/docs/latest-v22.x/api/sqlite.html), [Node v26.5.1 `node:sqlite`](https://nodejs.org/docs/latest/api/sqlite.html)

SQLite allows multiple concurrent read transactions across separate processes, but only one write transaction per database file at a time. In rollback-journal mode, `BEGIN EXCLUSIVE` prevents other connections from reading during the transaction; in WAL mode, `EXCLUSIVE` behaves identically to `IMMEDIATE` and **cannot** be used to exclude readers. The SQLite rollback pager has SHARED, RESERVED, PENDING, and EXCLUSIVE states; PENDING prevents new readers from joining, with the goal of avoiding writer starvation. A hot journal left by a crash is rolled back before the next read. [SQLite transaction modes](https://www.sqlite.org/lang_transaction.html), [SQLite locking states, writer starvation, and hot-journal recovery](https://www.sqlite.org/lockingv3.html)

Thus, if policy permits, **each resource can be made into its own SQLite database file**: a shared lease holds a SELECT read transaction; an exclusive lease holds `BEGIN EXCLUSIVE` in explicit non-WAL rollback-journal mode; upon process death the OS file locks disappear and the unfinished transaction is rolled back by SQLite. A lifecycle DB can express global exclusive against all Projects' shared lifecycle; different Projects/fingerprints use different DB files to retain mutual parallelism. The fixed rank is still acquired file-by-file in JS and is not cross-DB atomic acquisition.

### Why It Is Not a Suitable Replacement for the Current Approach

1. **A single DB has no arbitrary row-level lock concurrency.** Even with different resource rows in one table, SQLite still has only one simultaneous write transaction; using row insert/delete to represent holders unnecessarily serializes different Projects. If shared holders each insert lease rows in long write transactions, uncommitted data is invisible to each other and multiple writers cannot coexist. Preserving resource isolation requires resource-per-file, or building a separate heartbeat lease protocol.
2. **WAL mode is a correctness switch that is easy to trip.** If any initialization or existing default changes to WAL, `BEGIN EXCLUSIVE` no longer excludes readers; the global barrier semantics change. The implementation must fix and verify rollback journal mode, adding a SQLite-specific invariant. [SQLite `EXCLUSIVE` in WAL](https://www.sqlite.org/lang_transaction.html#deferred_immediate_and_exclusive_transactions)
3. **Waiting cannot be directly cancelled.** `DatabaseSync`'s busy timeout sleeps inside a synchronous native call; the Node API does not accept `AbortSignal` on a pending `BEGIN EXCLUSIVE`. SQLite's official busy timeout only repeatedly sleeps until the accumulated milliseconds elapse, then returns `SQLITE_BUSY`, with no FIFO promise. [SQLite busy timeout](https://www.sqlite.org/c3ref/busy_timeout.html) To meet cancellation, one can only set `timeout: 0`/short timeout and poll in JS with an abortable timer; this abandons SQLite's internal wait queue and introduces polling load and unfair competition.
4. **Fairness has only partial guarantees.** The rollback pager's PENDING state can block new readers and reduce writer starvation, but the official documentation does not declare FIFO for multiple waiting writers or for an entire set of arbitrary resources. JS short polling offers even less arrival-order guarantee.
5. **Introduces persistent coordinator artifacts.** A `:memory:` database cannot be shared by independent processes; cross-process requires a file-backed DB. Resource-per-file persistently leaves SQLite headers/schemas, and transactions may produce rollback journals/hot journals. This is not Platform "generation", but it is genuinely new persistent lock-coordinator state, unlike the current approach of using an ordinary file with no domain state as a kernel lock target; under this study's "no persistent state" constraint this is a violation.
6. **Incomplete Node version coverage.** If `>=22` genuinely includes v22.0–v22.4, `node:sqlite` is absent; the v22 line has also been experimental throughout. A more precise minimum patch must be raised, which still does not resolve the semantic and policy issues above.

**Devbox analysis:** SQLite comes closest to "no extra binary, kernel crash recovery, shared/exclusive", but the cost of obtaining these properties is persistent resource-per-file databases, a journal-mode invariant, and abortable polling. It turns a small lock adapter into a database lifecycle subsystem, does not meet the current no persistent coordinator state constraint, and is more complex than directly holding an advisory-lock FD.

## Candidate 5: Native Addon

A Node-API addon can directly wrap Linux `flock(2)` or `F_OFD_SETLK`: JS still decides resource paths, ranks, diagnostics, and `AbortSignal`; the addon only performs syscalls. The FD is held by the main Node process; normal close or process death releases it via the kernel, with no need for heartbeat/PID stale detection. For the current WSL2-only scope, this can be semantically equivalent to the helper.

But the addon must avoid throwing an uncancellable blocking `flock(LOCK_EX)` directly into the worker pool and then pretending the Promise is cancellable. A reliable design should expose `LOCK_NB` and let JS perform abortable backoff; or provide a native mechanism that can genuinely interrupt the wait. The first-party `fs-ext` source demonstrates the nature of the common approach: JS `require('./build/Release/fs_ext.node')`, strings `sh`/`ex` mapping to `LOCK_SH`/`LOCK_EX`, C++ calling `flock` in a libuv work item; its public callback API has no `AbortSignal`. The package's install script is `node-gyp configure build` and depends on NAN, making it a typical npm native addon rather than pure JS. [`fs-ext` JS binding](https://github.com/baudehlo/node-fs-ext/blob/master/fs-ext.js), [`fs-ext` native `flock` source](https://github.com/baudehlo/node-fs-ext/blob/master/fs-ext.cc), [`fs-ext` package build](https://github.com/baudehlo/node-fs-ext/blob/master/package.json)

Node-API can spare a self-maintained addon from rebuilding for every Node major, but still requires building, packaging, loading, and verifying the `.node` binary for `linux-x64`; if using an off-the-shelf NAN addon, the Node/V8 ABI and maintenance risk are higher. Crash release removes one layer of parent-EOF protocol compared to the helper, but an addon crash also directly brings down the CLI process, and native memory-safety/ABI issues enter the main process. This is a viable path for "removing the Go executable", not for "going pure JS".

## Candidate 6: External Precompiled Helper

The current exact-version `devbox-host` is the narrowest native seam: one child only holds kernel advisory-lock FDs, reports ready/error/release via versioned JSONL, and carries no Project or domain policy. Linux `flock` provides the required shared/exclusive and close-on-exit ownership; when the parent crashes the pipe writer closes, the child sees EOF and exits, and the helper exit causes the kernel to release the FD. A pipe reader only sees EOF after **all** write-end references are closed, so the implementation/spawn must avoid inadvertently duplicating the stdin writer FD. [Linux `pipe(7)` EOF semantics](https://man7.org/linux/man-pages/man7/pipe.7.html), [Linux `flock(2)` close release](https://man7.org/linux/man-pages/man2/flock.2.html)

Its drawbacks are platform executable distribution, child startup/protocol, and version handshake; it also cannot claim strict FIFO for kernel waiters. However, Devbox already has an exact same-version platform package for v1 `linux/amd64`, and helper crashes and malformed protocol can be isolated as child failures. Compared to a native addon, it does not load native code into the CLI address space; compared to all marker leases, it needs no stale timeout; compared to socket/SQLite, it introduces no coordinator state.

## Historical Conditional Recommendations

### 1. Existing Requirements Unchanged: Retain Go Helper

Retain the current "TypeScript policy + extremely narrow native lock holder" boundary. This is the only already-chosen solution that simultaneously meets cross-independent-process, shared/exclusive, Project parallelism/global barrier, ranked acquisition, wait cancellation, crash/EOF auto-release, and no daemon/socket/persistent lease state. Go is not a semantic necessity; **a native component capable of holding kernel advisory-lock FDs** is the necessity. But since binary packaging already exists, moving the same syscall into an addon yields no "pure JS" benefit.

### 2. If Only Removing Go/Child: Could Switch to Node-API Addon, but Must Acknowledge It Remains a Native Solution

Consider only if measurement shows child startup/protocol is an actual problem, or the team has a clear preference for maintaining C/Rust Node-API over Go. Minimum design conditions:

- Own, minimal Node-API addon; do not directly adopt the blocking `fs-ext` API that lacks `AbortSignal`;
- Expose nonblocking shared/exclusive acquire and unlock, with clear FD lifetime;
- JS continues to use fixed rank, abortable backoff, reverse release, and waiting-resource diagnostics;
- `linux-x64` prebuild placed in the existing platform package, with ABI, mode, and runtime load failure verification;
- Keep independent open file descriptions per resource, avoiding the traditional process-associated `fcntl` trap of "any close clears all locks"; prefer `flock` or Linux OFD lock.

This can remove the helper process; it cannot remove the precompiled native artifact, and the native bug blast radius is larger.

### 3. Truly Pure JS Deployment: Only Possible If Requirements Are Reduced

- **Switch to threads within a single resident Node process:** Raise minimum to Node >=24.5, use `worker_threads.locks`; simultaneously give up "independent CLI processes" or accept a new daemon.
- **Exclusive only, and tolerate manual cleanup/permanent stall after crash:** `mkdir`/`O_EXCL` can preserve safety; give up automatic crash release.
- **Exclusive only, and tolerate stale timeout and pause/suspend split brain:** Can use mature lockfile heartbeat; give up current reliability, especially unsuitable for Docker/Platform publication.
- **Linux exclusive name only, and tolerate live sockets:** Abstract Unix bind can achieve both immediate crash release and no persistent marker; give up shared/global reader barrier and no-socket.
- **Tolerate socket coordinator/daemon:** Can implement full RW queue, fairness, rank, and cancellation in memory, but must add a protocol for all clients to fail-stop on coordinator crash.
- **Tolerate persistent coordinator files, resource-per-file, and polling cancellation:** Can investigate rollback-mode SQLite transactions; simultaneously raise the Node minimum patch, lock the journal mode, and accept it as Node built-in native rather than pure JS implementation.

## Is a Narrow Prototype Needed?

A prototype is not needed to answer "can we go pure JS under the existing contract": Node process scope, `O_EXCL` ownership, Unix socket lifetime, and SQLite transaction scope are all directly decided by primary sources, and marker leases have structural counterexamples in the paused-live-owner scenario.

If a future decision changes to "allow native addon, only compare addon vs. Go helper", a narrow prototype that **does not enter production code** can be built to reduce the only remaining valuable uncertainty: on WSL2 `linux/amd64`, use a minimal Node-API wrapper exposing `flock(LOCK_SH/LOCK_EX|LOCK_NB)`, validated by three independent Node processes for shared/shared, shared/exclusive, different-resource parallelism, fixed-rank waiting, abort during wait, immediate acquisition after holder `SIGKILL`, and loading the same prebuild on Node 22 and the current version. What it answers is ABI/package/cancellation engineering cost; it does not turn the addon into pure JS, nor does it need to re-verify lock semantics already established by kernel documentation.

## Final Answer

The current answer is not "pure JavaScript locking is safe under the former crash-release contract." The current pre-release decision deliberately reduces that contract: it removes Go and native locking, uses simple command markers, rejects busy operations immediately, and documents manual cleanup after forced termination. This is accepted because keeping the package simple and allowing different Projects to run `up` concurrently is more important for the current scope than automatic recovery of abandoned markers. Future native coordination remains an open decision for operations that modify shared Docker or Platform artifacts.
